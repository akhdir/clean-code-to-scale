0:00–0:35 · Concept

CAP, messaging, and how failure spreads

"Consistency, availability, partition tolerance — pick two" is the famous phrasing, and it's a slight oversimplification worth correcting properly before using it.

Beyond CAP — PACELC. CAP only governs behavior during a partition. The rest of the time, a distributed system still trades Latency against Consistency: a strongly-consistent read across regions is slower than an eventually-consistent one, partition or not. If OrderService and InventoryService live in the same region, PACELC's else clause is the tradeoff you're living with every single request — not just the rare partition.

CAP & consistency

  • Partitions happen; the real choice is Consistency vs. Availability during one
  • Strong consistency: every read sees the latest write, everywhere
  • Eventual consistency: reads may be briefly stale, but converge
  • PACELC: even with no partition, trade Latency against Consistency

Sync vs. async

  • Sync: simple mental model, but couples your availability to theirs
  • Async (queue/event): decouples timing, adds durability — and eventual consistency
  • Ask: does the caller need the result now to proceed, or can it happen eventually?
  • At-least-once delivery means the handler must be idempotent

Containing failure

  • Every synchronous call needs a timeout — a hang anywhere becomes a hang everywhere
  • Retries: only for transient, idempotent calls, with backoff and jitter
  • Circuit breaker: stop calling a failing dependency; fail fast, let it recover
  • Bulkheads: isolate resource pools so one slow dependency can't starve the rest
0:35–1:10 · Live demo

Dissecting a cascading failure

A single external dependency having a slow afternoon takes down the entire checkout flow. Walk the timeline first, then the code that let it happen.

10:02

FraudCheckAPI (external, third-party) starts responding in 30s instead of its usual 200ms — their incident, not ours.

10:03

PaymentService calls it with no timeout. Every request thread waiting on a fraud check now blocks for the full 30s.

10:06

PaymentService's thread pool is fully occupied waiting. New requests to PaymentService — for anything, not just fraud checks — start queuing.

10:08

OrderService calls PaymentService with no timeout either. Its threads now block waiting on a service that's blocked waiting on FraudCheckAPI.

10:11

Checkout is down, site-wide. The original problem was one external dependency having a bad ten minutes.

payment_service.py — beforeno timeout, no breaker, no fallback
def confirm_payment(order):
    fraud_result = fraud_check_api.check(order)
    if fraud_result.flagged:
        return reject(order)
    return charge_payment(order)
payment_service.py — aftertimeout + circuit breaker + fallback
fraud_breaker = CircuitBreaker(
    failure_threshold=5,
    reset_after_seconds=30,
)

def confirm_payment(order):
    try:
        fraud_result = fraud_breaker.call(
            lambda: fraud_check_api.check(order, timeout=2.0)
        )
    except (CircuitOpenError, TimeoutError):
        # the dependency is having a bad day — don't have one too
        return flag_for_manual_review(order)

    if fraud_result.flagged:
        return reject(order)
    return charge_payment(order)
Talking points
  1. The 2-second timeout is the whole fix for the cascade — it caps how long one bad dependency can hold a thread, no matter what the dependency does.
  2. The circuit breaker is what stops retrying a dependency that's already down from making things worse — after 5 failures, it stops trying for 30 seconds and fails fast instead.
  3. flag_for_manual_review is a real fallback, not an error page — the business kept operating, just more slowly and more manually, for the orders that needed it.
  4. This wasn't a synchronous-vs-async decision we get to relitigate here — fraud checks that gate a charge need an answer before the charge happens. The fix is containment, not switching to async.

Contain a flaky call chain

Work in pairs. get_shipping_estimate below can hang checkout entirely over something that was never worth blocking on.

Add a timeout, a bounded retry, and a circuit breaker

TaskChange checkout so a struggling shipping_rate_api never blocks the order. Add a timeout, a bounded retry with backoff (only if the call is safe to retry), a circuit breaker, and a flat-rate fallback for when the circuit is open.
shipping.pystarter
def get_shipping_estimate(order):
    rate = shipping_rate_api.get_rate(order.destination, order.weight)
    return rate

def checkout(order):
    estimate = get_shipping_estimate(order)
    order.shipping_cost = estimate
    return finalize_order(order)
  • Is get_rate idempotent? What would make you decide not to retry it?
  • What's the right fallback when the circuit is open — fail the whole checkout, or degrade gracefully? What does "degrade gracefully" actually mean for a shipping estimate?
  • How would you test that the circuit breaker genuinely opens, without waiting for a real outage to happen?
Done when
  • checkout never hangs on shipping_rate_api alone, no matter how it fails
  • The retry only fires for the failure modes you decided were safe to retry
  • You can state, in one sentence, what a customer sees when the circuit is open

Answer key — shipping.py 
shipping_breaker = CircuitBreaker(failure_threshold=5, reset_after_seconds=30)
FLAT_RATE_FALLBACK = 7.99

def get_shipping_estimate(order):
    def attempt():
        return shipping_rate_api.get_rate(
            order.destination, order.weight, timeout=1.5
        )

    for attempt_number in range(2):  # one retry — a rate lookup is a safe GET
        try:
            return shipping_breaker.call(attempt)
        except CircuitOpenError:
            return FLAT_RATE_FALLBACK
        except TimeoutError:
            if attempt_number == 1:
                return FLAT_RATE_FALLBACK
            time.sleep(0.2)  # brief backoff before the one retry

def checkout(order):
    order.shipping_cost = get_shipping_estimate(order)
    return finalize_order(order)

The flat rate is a real business decision, not a placeholder — someone has to decide it's an acceptable customer experience before this ships. That conversation is itself part of "done."
