Everything today assumes you know what a class and a subclass are. If that's already second nature, skip straight to the five principles below — if not, these two ideas are all of the prerequisite this session has.

What is a class?

A class is a blueprint for creating objects that bundle related data (called attributes) and behavior (called methods) together — instead of passing loose variables around to separate functions that operate on them.

primer.pya class, and an object made from it
class Employee:
    def __init__(self, name, hourly_rate):
        self.name = name
        self.hourly_rate = hourly_rate     # attribute: data this object holds
        self.vacation_days = 15             # attribute: every employee starts with 15

    def calculate_pay(self, hours):         # method: behavior this object can do
        return hours * self.hourly_rate

    def describe(self):                     # method: reads the attributes above
        return f"{self.name}: {self.vacation_days} vacation days/year"

employee = Employee("Sam", 25)   # an object — one instance built from the class
print(employee.calculate_pay(40))
# prints: 1000

The class is the blueprint; employee is one specific object built from it. Call Employee(...) again with a different name and rate and you get a second, independent object — same blueprint, its own data. Every class you see for the rest of today is built the same way: attributes plus methods.

What is inheritance (a.k.a. extension)?

Inheritance lets one class reuse another class's attributes and methods, then add its own or override the ones it doesn't like. The new class (the subclass) is a more specific version of the original (the superclass) — anywhere an Employee is expected, a Manager can stand in for it, because it is one.

primer.pya subclass extending Employee
class Manager(Employee):              # Manager extends (inherits from) Employee
    def calculate_pay(self, hours):   # overrides calculate_pay with its own version
        return hours * self.hourly_rate * 1.15   # managers earn a 15% bonus

    # no __init__, no vacation_days, no describe() here —
    # Manager never writes any of that itself

manager = Manager("Jordan", 25)
print(manager.calculate_pay(40))
# prints: 1150.0
# Manager's own calculate_pay() ran, not Employee's

print(manager.describe())
# prints: Jordan: 15 vacation days/year
# describe() and vacation_days came from Employee, untouched —
# that's the actual value of inheritance: free reuse of the
# 90% that doesn't change, not just permission to override

class Manager(Employee): is Python's syntax for "Manager inherits from Employee." Every principle in this session, and every pattern, is really a rule of thumb about using these two ideas — classes and inheritance — without them turning on you as the codebase grows.

0:00–1:30 · Concept

Five letters, five failures

Each principle is a named answer to a way codebases actually break. Read all five — today's demo and kata both live mostly in the last one.

S
Single Responsibility — one reason to change

A class doing two unrelated jobs will get edited for either reason, by people who don't know about the other.

Example: an InvoiceGenerator that also formats and sends emails has two reasons to change: pricing rules, and email wording.
O
Open/Closed — open for extension, closed for modification

Adding new behavior should mean adding new code, not editing code that already works and is already tested.

Example: a new discount type shouldn't mean editing an if/elif chain — it should mean adding one new class.
L
Liskov Substitution — a subclass shouldn't surprise the caller

Anywhere the parent type is expected, a subclass should work the same way, not throw or silently do nothing.

Example: a GiftCardPayment that raises on .refund() breaks any caller that trusts every Payment supports it.
I
Interface Segregation — don't force unused methods

A class shouldn't have to implement a method it has no use for, just because it shares an interface with something that does.

Example: a RobotWorker forced to implement .eat_lunch() and .sleep() only because every Worker does.
D
Dependency Inversion — depend on abstractions, not concretions

A class that constructs its own dependencies is welded to them. A class that receives them can have them swapped — for production, or for a test.

Example: an OrderService that builds a PostgresRepository inside itself, instead of receiving a repository interface.

O, L, and I, made concrete

S and D carry today's demo and kata — here's one violation each for the three letters that otherwise stay theoretical, issue and fix. O's example is deliberately not another discount chain — you'll see enough of those today.

Open/ClosedAn order-status handler with one elif per status. Every new status means editing a function that already works, and re-testing the ones that already did.
def handle_status_change(order):
    if order.status == "paid":
        send_confirmation_email(order)
    elif order.status == "shipped":
        send_tracking_email(order)
    elif order.status == "delivered":
        request_review(order)
    elif order.status == "cancelled":
        send_cancellation_email(order)

# adding "refunded" means editing this function and
# re-testing every status that already worked
The fix — a lookup table, not a chain
STATUS_HANDLERS = {
    "paid": send_confirmation_email,
    "shipped": send_tracking_email,
    "delivered": request_review,
    "cancelled": send_cancellation_email,
}

def handle_status_change(order):
    handler = STATUS_HANDLERS.get(order.status)
    if handler:
        handler(order)

# adding "refunded" is one new dict entry —
# handle_status_change never changes again

Strategy classes aren't the only way to satisfy OCP — a plain lookup table works too, and reads more naturally when each "behavior" is already just a function, with no state of its own to carry.

Liskov SubstitutionEvery Payment is supposed to support .refund(). A gift card can't be — so code that trusts the contract crashes the moment one shows up in the list.
class Payment:
    def refund(self, amount): raise NotImplementedError

class CreditCardPayment(Payment):
    def refund(self, amount):
        gateway.refund(self.card_token, amount)

class GiftCardPayment(Payment):
    def refund(self, amount):
        raise NotImplementedError("not refundable")

# works fine until a GiftCardPayment is in the list
for payment in customer.payments:
    payment.refund(order.total)  # boom, eventually
The fix — refund becomes its own capability
class Payment:
    ...  # whatever every payment shares

class Refundable:
    def refund(self, amount): raise NotImplementedError

class CreditCardPayment(Payment, Refundable):
    def refund(self, amount):
        gateway.refund(self.card_token, amount)

class GiftCardPayment(Payment):
    # no refund() at all — never a real capability
    pass

# the caller asks, instead of assuming
refundable = [p for p in customer.payments
              if isinstance(p, Refundable)]
for payment in refundable:
    payment.refund(order.total)
Interface SegregationThe classic version of this smell: a Worker interface with a lunch break and a sleep schedule — two things a robot doesn't have.
class Worker:
    def work(self): raise NotImplementedError
    def eat_lunch(self): raise NotImplementedError
    def sleep(self): raise NotImplementedError

class HumanWorker(Worker):
    def work(self): assemble_parts()
    def eat_lunch(self): take_break()
    def sleep(self): clock_out()

class RobotWorker(Worker):
    def work(self): assemble_parts()
    def eat_lunch(self):
        raise NotImplementedError("robots don't eat")
    def sleep(self):
        raise NotImplementedError("robots don't sleep")

# RobotWorker answers to a lunch break and a sleep
# schedule — neither has anything to do with welding
The fix — split the fat interface in two
class Workable:
    def work(self): raise NotImplementedError

class Schedulable:
    def eat_lunch(self): raise NotImplementedError
    def sleep(self): raise NotImplementedError

class HumanWorker(Workable, Schedulable):
    def work(self): assemble_parts()
    def eat_lunch(self): take_break()
    def sleep(self): clock_out()

class RobotWorker(Workable):
    def work(self): assemble_parts()
    # no eat_lunch or sleep — never had a use for either

# only ask Schedulable workers to clock out
for worker in shift.workers:
    if isinstance(worker, Schedulable):
        worker.sleep()

Patterns you already have the tools for

A "design pattern" is usually just one of these five principles, applied to a recurring shape. Each one below is the same code, twice — without the pattern, then with it.

StrategyOCP · DIPYou already built this — it's DiscountStrategy in today's live demo, shown here in miniature.
Without it
def calculate_discount(total, discount_type):
    if discount_type == "loyalty":
        return total * 0.9
    elif discount_type == "seasonal":
        return total * 0.85
    elif discount_type == "employee":
        return total * 0.7
    return total

# adding "student" means editing this function,
# and re-testing every branch that's already there
With Strategy
class DiscountStrategy:
    def apply(self, total): raise NotImplementedError

class SeasonalDiscount(DiscountStrategy):
    def apply(self, total): return total * 0.85

# adding "student" means adding a class —
# this line never changes again
total = discount.apply(total)

What improved: the function that varies is gone. Nothing left to re-test when a discount type is added — there's only something to add.

Factory MethodDIP · OCPCentralizes object construction in one place, instead of an if/elif scattered across every call site that needs one.
Without it
# repeated at every call site that needs a notifier
if customer.channel == "email":
    notifier = EmailNotifier(smtp_host="smtp.x.com")
elif customer.channel == "sms":
    notifier = SmsNotifier(api_key="xxxx")
notifier.send(message)

# ...copy-pasted again, three files over
With Factory Method
class NotifierFactory:
    def create(self, channel):
        if channel == "email": return EmailNotifier()
        if channel == "sms": return SmsNotifier()
        raise ValueError(channel)

# every call site asks, none of them decide
notifier = NotifierFactory().create(customer.channel)
notifier.send(message)

What improved: the construction logic lived in five places before — a new channel meant finding and editing all five, and missing one was a silent bug. Now it exists once.

DecoratorOCP · SRPAdds behavior by wrapping an object, not editing it. Today's new kata builds one of these on a repository.
Without it
class EmailNotifier:
    def send(self, to, message):
        for attempt in range(3):
            try:
                smtp.send(to, message)
                return
            except SmtpError:
                if attempt == 2: raise
                time.sleep(0.5)

# every notifier class repeats this same retry loop
With Decorator
class RetryingNotifier:
    def __init__(self, notifier, attempts=3):
        self.notifier = notifier
        self.attempts = attempts

    def send(self, to, message):
        for attempt in range(self.attempts):
            try:
                return self.notifier.send(to, message)
            except SmtpError:
                if attempt == self.attempts - 1: raise
                time.sleep(0.5)

notifier = RetryingNotifier(EmailNotifier())

What improved: the retry loop was copy-pasted into every notifier before. Now it wraps any of them once, and EmailNotifier goes back to just sending email.

ObserverSRP · DIPThe subject doesn't know or care what reacts to it — only that something might want to. Full implementation below, not just the usage.
Without it
class OrderService:
    def place_order(self, order):
        save_order(order)
        send_confirmation_email(order)
        update_analytics(order)
        notify_warehouse(order)

# "text the courier too" means editing this method,
# and OrderService now knows about four other teams
With Observer — the whole implementation
class OrderEvents:
    def __init__(self):
        self._subscribers = []

    def on_placed(self, callback):
        self._subscribers.append(callback)

    def emit(self, order):
        for callback in self._subscribers:
            callback(order)

# wiring: each team subscribes itself, on startup
order_events = OrderEvents()
order_events.on_placed(send_confirmation_email)
order_events.on_placed(update_analytics)
order_events.on_placed(notify_warehouse)

# the subject: doesn't import or know about any of them
class OrderService:
    def __init__(self, events):
        self.events = events

    def place_order(self, order):
        save_order(order)
        self.events.emit(order)

What improved: place_order() used to grow a line for every team that cared about a new order. Now it emits one event — subscribing is each team's job, not OrderService's. Note events arrives through the constructor, not a global — DIP again, doing the same job it does everywhere else today.

1:30–2:10 · Live demo

One god class, refactored on screen

Live-code the transformation rather than pasting the finished version. This one class manages to violate three of the five principles at once — find them before revealing the talking points.

order_processor.py — beforeSRP, OCP, DIP all violated
class OrderProcessor:
    def __init__(self):
        self.db = PostgresDatabase()
        self.email = SmtpEmailService()

    def process(self, order):
        if not order.items:
            raise ValueError("empty order")

        total = sum(i.price * i.qty for i in order.items)

        if order.discount_type == "loyalty":
            total *= 0.9
        elif order.discount_type == "seasonal":
            total *= 0.85
        elif order.discount_type == "employee":
            total *= 0.7

        self.db.save(order.id, total)
        self.email.send(order.customer_email, f"Your total: ${total:.2f}")
        return total
Talking points — before
  1. OrderProcessor has at least three reasons to change: pricing math, discount rules, and email wording. SRP says it should have one.
  2. The if/elif discount chain means every new discount type means editing this method — the exact thing OCP says shouldn't happen.
  3. PostgresDatabase() and SmtpEmailService() are built right inside __init__. Swap either one — a test double, a different provider — and you have to edit this class. That's DIP, inverted the wrong way.
order_processor.py — afterone job each, new discounts add a class
class DiscountStrategy:
    def apply(self, total): raise NotImplementedError

class LoyaltyDiscount(DiscountStrategy):
    def apply(self, total): return total * 0.9

class SeasonalDiscount(DiscountStrategy):
    def apply(self, total): return total * 0.85

class EmployeeDiscount(DiscountStrategy):
    def apply(self, total): return total * 0.7

class NoDiscount(DiscountStrategy):
    def apply(self, total): return total

# repository and notifier are received, not constructed (DIP)
class OrderProcessor:
    def __init__(self, repository, notifier):
        self.repository = repository
        self.notifier = notifier

    def process(self, order, discount: DiscountStrategy):
        if not order.items:
            raise ValueError("empty order")
        total = sum(i.price * i.qty for i in order.items)
        total = discount.apply(total)
        self.repository.save(order.id, total)
        self.notifier.notify(order.customer_email, total)
        return total
Talking points — after
  1. OrderProcessor now does one thing: orchestrate. Pricing lives in DiscountStrategy subclasses, persistence in repository, notification in notifier.
  2. A new discount type is a new class, not a new elif — process() never changes again for a pricing change. That's OCP.
  3. repository and notifier are passed in, not constructed — swap a fake in for a test, or a different provider in production, without touching OrderProcessor. That's DIP, and it's exactly what makes this class trivially testable now.
  4. Any DiscountStrategy subclass works anywhere DiscountStrategy is expected, because every one honors the same .apply(total) contract. That's LSP, and it fell out of the design for free.

InventoryAlert — invert two dependencies
35 minPairs
TaskChange InventoryAlert so it receives its notifier and clock through its constructor instead of building them itself. Don't change what check() does — only how its dependencies arrive.
inventory_alert.pystarter
class InventoryAlert:
    def __init__(self, threshold):
        self.threshold = threshold
        self.notifier = SlackNotifier(webhook_url="https://hooks.slack.com/T000/B000/xxxx")
        self.clock = SystemClock()

    def check(self, item):
        if item.stock < self.threshold:
            timestamp = self.clock.now()
            self.notifier.send(f"[{timestamp}] Low stock: {item.name} ({item.stock} left)")
  • What would you have to do today to unit test check() without actually pinging Slack?
  • What does InventoryAlert actually need from a notifier — the smallest possible interface — versus what SlackNotifier offers?
  • If tomorrow you needed to alert by email instead, how many lines of InventoryAlert would you touch today — and how many after your fix?

  • InventoryAlert.__init__ takes notifier and clock as parameters, not constructs them
  • You can state, in one sentence, the minimal shape a notifier needs — that sentence is the abstraction you just found
RepositoryDecorators — wrap it, don't edit it
20 minPairs
TaskPostgresRepository.save() below does three unrelated jobs: persist, time-and-log, and retry. Pull logging and retry out into decorators that wrap any object with a .save(order_id, total) method — so PostgresRepository goes back to doing exactly one thing.
order_repository.pystarter
class PostgresRepository:
    def save(self, order_id, total):
        start = time.time()
        for attempt in range(3):
            try:
                db.execute(
                    "INSERT INTO orders (id, total) VALUES (%s, %s)",
                    order_id, total,
                )
                log.info(f"saved order {order_id} in {time.time() - start:.2f}s")
                return
            except ConnectionError:
                if attempt == 2:
                    raise
                time.sleep(0.5)
Why this kata only works because of the last one — OrderProcessor.process() already receives repository instead of constructing it. Decorator needs exactly that seam to attach to: without DIP, there's nowhere to slide a wrapper in.
  • What does PostgresRepository.save() have to do with logging or retries, conceptually? Name its one real job.
  • If OrderProcessor from today's demo receives a decorated repository instead of a plain one, how many lines of OrderProcessor change?
  • Which decorator would you want to skip in a test — and can you, without touching PostgresRepository?
Done when
  • PostgresRepository.save() only persists — no timing, no logging, no retry
  • Logging and retry each exist as their own class that wraps any repository-shaped object, not just PostgresRepository
  • You can compose them in either order without editing any of the three classes
SubscriptionManager — reduce the responsibilities
~15 minStretch
TaskFinished both core katas early? renew() below validates, prices, charges, updates state, and emails — four reasons to change in one method. Split it so renew() only orchestrates, and every extracted piece has exactly one reason to change.
subscription_manager.pystarter
class SubscriptionManager:
    def __init__(self, payment_gateway, email_service):
        self.payment_gateway = payment_gateway
        self.email_service = email_service

    def renew(self, subscription, plan):
        if plan not in ("monthly", "annual"):
            raise ValueError("unknown plan")

        price = 29.00 if plan == "monthly" else 290.00

        self.payment_gateway.charge(subscription.customer_id, price)

        subscription.plan = plan
        subscription.renewed_at = datetime.now()

        self.email_service.send(
            subscription.customer_email,
            f"Your {plan} subscription has been renewed for ${price:.2f}"
        )
  • How many reasons does renew() have to change today? Name each one.
  • Which extracted piece — validation, pricing, or notification — would you want unit tested directly, without a real payment gateway?
  • If a third plan type is added tomorrow, how many places in your refactor need to change?
Done when
  • renew() reads as a short ordered list of calls, not inline logic
  • Each extracted piece has exactly one reason to change, and you can name it

When is SOLID too much?

Ask the room

Where have you seen SOLID applied so eagerly that a 10-line script became five files? What was actually gained?

Ask tech leads

What's your team's real signal for "this needs an interface" — is it written down, or does it live in one person's head?

Ask QEs

Does an interface you can't easily fake in a test actually satisfy DIP, or does it just look like it does?

Ask AI engineers

An agent told to "make this more SOLID" will often add interfaces everywhere. When is that right, and when is it exactly the over-engineering this session warns about?

Before the room breaks, each person commits to one:

Find one place a concrete dependency is constructed inside a class instead of passed in
Delete one interface with exactly one implementation that will likely only ever have one

Answer key — RepositoryDecorators 
class PostgresRepository:
    def save(self, order_id, total):
        db.execute(
            "INSERT INTO orders (id, total) VALUES (%s, %s)",
            order_id, total,
        )

class LoggingRepository:
    def __init__(self, repository):
        self.repository = repository

    def save(self, order_id, total):
        start = time.time()
        self.repository.save(order_id, total)
        log.info(f"saved order {order_id} in {time.time() - start:.2f}s")

class RetryingRepository:
    def __init__(self, repository, attempts=3):
        self.repository = repository
        self.attempts = attempts

    def save(self, order_id, total):
        for attempt in range(self.attempts):
            try:
                return self.repository.save(order_id, total)
            except ConnectionError:
                if attempt == self.attempts - 1:
                    raise
                time.sleep(0.5)

# compose in either order — neither class knows about the other
repository = LoggingRepository(RetryingRepository(PostgresRepository()))
processor = OrderProcessor(repository, notifier)

OrderProcessor doesn't change at all — it still just calls repository.save(order_id, total). That's only possible because process() already receives repository instead of constructing it; Decorator is DIP's seam, used a second time.

    def renew(self, subscription, plan):
        self.validator.validate(plan)
        price = self.pricing.price_for(plan)
        self.payment_gateway.charge(subscription.customer_id, price)
        subscription.mark_renewed(plan)
        self.email_service.send_renewal_notice(subscription, plan, price)

A third plan is a new entry in PRICES and VALID_PLANS — not a new elif in renew(). That's the OCP payoff of splitting pricing out on its own.

Answer key — Factory Method quick rep (database connections) 
class ConnectionFactory:
    def create(self, env):
        if env == "production":
            return PostgresConnection(host="prod.db.internal")
        if env == "staging":
            return PostgresConnection(host="staging.db.internal")
        if env == "local":
            return SqliteConnection(path="local.db")
        raise ValueError(env)

# every script asks the factory — including the two other
# startup scripts that used to carry this same if/elif
connection = ConnectionFactory().create(env)

The if/elif itself didn't disappear — it moved to exactly one place. That's the whole fix: not "no branching," but "branching that lives once."

Answer key — Decorator quick rep (CachingPriceLookup) 
class CachingPriceLookup:
    def __init__(self, price_lookup):
        self.price_lookup = price_lookup
        self._cache = {}

    def get_price(self, sku):
        if sku not in self._cache:
            self._cache[sku] = self.price_lookup.get_price(sku)
        return self._cache[sku]

# a second call for the same SKU never reaches pricing_api
prices = CachingPriceLookup(PriceLookup())

PriceLookup never learns it's being cached — CachingPriceLookup just has to be shaped like one. Same seam as RepositoryDecorators, on a different object.

Answer key — Observer quick rep (InventoryService) 
class InventoryEvents:
    def __init__(self):
        self._subscribers = []

    def on_restocked(self, callback):
        self._subscribers.append(callback)

    def emit(self, item):
        for callback in self._subscribers:
            callback(item)

# wiring: each team subscribes itself, on startup
inventory_events = InventoryEvents()
inventory_events.on_restocked(send_restock_email)
inventory_events.on_restocked(update_reorder_forecast)

# the subject: doesn't import or know about either team
class InventoryService:
    def __init__(self, events):
        self.events = events

    def restock(self, item, qty):
        item.stock += qty
        self.events.emit(item)

Structurally identical to OrderEvents — a subscriber list, an on_X to join it, an emit to walk it. Once this shape is familiar, spotting where else it applies is the actual skill.
