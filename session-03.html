0:00–0:30 · Concept

Five letters, five failures

Each principle is a named answer to a way codebases actually break. Read all five — today's demo and kata both live mostly in the last one.

S
Single Responsibility — one reason to change

A class doing two unrelated jobs will get edited for either reason, by people who don't know about the other.

Example: an InvoiceGenerator that also formats and sends emails has two reasons to change: pricing rules, and email wording.
O
Open/Closed — open for extension, closed for modification

Adding new behavior should mean adding new code, not editing code that already works and is already tested.

Example: a new discount type shouldn't mean editing an if/elif chain — it should mean adding one new class.
L
Liskov Substitution — a subclass shouldn't surprise the caller

Anywhere the parent type is expected, a subclass should work the same way, not throw or silently do nothing.

Example: a Refund subclass of Payment that raises NotImplementedError on .charge() breaks every caller that trusts Payment.
I
Interface Segregation — don't force unused methods

A class shouldn't have to implement a method it has no use for, just because it shares an interface with something that does.

Example: a ReadOnlyReport forced to implement .save() only because every other Report does.
D
Dependency Inversion — depend on abstractions, not concretions

A class that constructs its own dependencies is welded to them. A class that receives them can have them swapped — for production, or for a test.

Example: an OrderService that builds a PostgresRepository inside itself, instead of receiving a repository interface.
0:30–1:10 · Live demo

One god class, refactored on screen

Live-code the transformation rather than pasting the finished version. This one class manages to violate three of the five principles at once — find them before revealing the talking points.

order_processor.py — beforeSRP, OCP, DIP all violated
class OrderProcessor:
    def __init__(self):
        self.db = PostgresDatabase()
        self.email = SmtpEmailService()

    def process(self, order):
        if not order.items:
            raise ValueError("empty order")

        total = sum(i.price * i.qty for i in order.items)

        if order.discount_type == "loyalty":
            total *= 0.9
        elif order.discount_type == "seasonal":
            total *= 0.85
        elif order.discount_type == "employee":
            total *= 0.7

        self.db.save(order.id, total)
        self.email.send(order.customer_email, f"Your total: ${total:.2f}")
        return total
Talking points — before
  1. OrderProcessor has at least three reasons to change: pricing math, discount rules, and email wording. SRP says it should have one.
  2. The if/elif discount chain means every new discount type means editing this method — the exact thing OCP says shouldn't happen.
  3. PostgresDatabase() and SmtpEmailService() are built right inside __init__. Swap either one — a test double, a different provider — and you have to edit this class. That's DIP, inverted the wrong way.
order_processor.py — afterone job each, new discounts add a class
class DiscountStrategy:
    def apply(self, total): raise NotImplementedError

class LoyaltyDiscount(DiscountStrategy):
    def apply(self, total): return total * 0.9

class SeasonalDiscount(DiscountStrategy):
    def apply(self, total): return total * 0.85

class EmployeeDiscount(DiscountStrategy):
    def apply(self, total): return total * 0.7

class NoDiscount(DiscountStrategy):
    def apply(self, total): return total

# repository and notifier are received, not constructed (DIP)
class OrderProcessor:
    def __init__(self, repository, notifier):
        self.repository = repository
        self.notifier = notifier

    def process(self, order, discount: DiscountStrategy):
        if not order.items:
            raise ValueError("empty order")
        total = sum(i.price * i.qty for i in order.items)
        total = discount.apply(total)
        self.repository.save(order.id, total)
        self.notifier.notify(order.customer_email, total)
        return total
Talking points — after
  1. OrderProcessor now does one thing: orchestrate. Pricing lives in DiscountStrategy subclasses, persistence in repository, notification in notifier.
  2. A new discount type is a new class, not a new elif — process() never changes again for a pricing change. That's OCP.
  3. repository and notifier are passed in, not constructed — swap a fake in for a test, or a different provider in production, without touching OrderProcessor. That's DIP, and it's exactly what makes this class trivially testable now.
  4. Any DiscountStrategy subclass works anywhere DiscountStrategy is expected, because every one honors the same .apply(total) contract. That's LSP, and it fell out of the design for free.
1:10–1:45 · Hands-on

Invert the dependency

Work in pairs. InventoryAlert below builds its own dependencies instead of receiving them — the same DIP violation as the god class, in miniature.

InventoryAlert — invert two dependencies
35 minPairs
TaskChange InventoryAlert so it receives its notifier and clock through its constructor instead of building them itself. Don't change what check() does — only how its dependencies arrive.
inventory_alert.pystarter
class InventoryAlert:
    def __init__(self, threshold):
        self.threshold = threshold
        self.notifier = SlackNotifier(webhook_url="https://hooks.slack.com/T000/B000/xxxx")
        self.clock = SystemClock()

    def check(self, item):
        if item.stock < self.threshold:
            timestamp = self.clock.now()
            self.notifier.send(f"[{timestamp}] Low stock: {item.name} ({item.stock} left)")
  • What would you have to do today to unit test check() without actually pinging Slack?
  • What does InventoryAlert actually need from a notifier — the smallest possible interface — versus what SlackNotifier offers?
  • If tomorrow you needed to alert by email instead, how many lines of InventoryAlert would you touch today — and how many after your fix?
Done when
  • InventoryAlert.__init__ takes notifier and clock as parameters, not constructs them
  • You can state, in one sentence, the minimal shape a notifier needs — that sentence is the abstraction you just found
SubscriptionManager — reduce the responsibilities
~15 minStretch
TaskFinished the DIP kata early? renew() below validates, prices, charges, updates state, and emails — four reasons to change in one method. Split it so renew() only orchestrates, and every extracted piece has exactly one reason to change.
subscription_manager.pystarter
class SubscriptionManager:
    def __init__(self, payment_gateway, email_service):
        self.payment_gateway = payment_gateway
        self.email_service = email_service

    def renew(self, subscription, plan):
        if plan not in ("monthly", "annual"):
            raise ValueError("unknown plan")

        price = 29.00 if plan == "monthly" else 290.00

        self.payment_gateway.charge(subscription.customer_id, price)

        subscription.plan = plan
        subscription.renewed_at = datetime.now()

        self.email_service.send(
            subscription.customer_email,
            f"Your {plan} subscription has been renewed for ${price:.2f}"
        )
  • How many reasons does renew() have to change today? Name each one.
  • Which extracted piece — validation, pricing, or notification — would you want unit tested directly, without a real payment gateway?
  • If a third plan type is added tomorrow, how many places in your refactor need to change?
Done when
  • renew() reads as a short ordered list of calls, not inline logic
  • Each extracted piece has exactly one reason to change, and you can name it
1:45–2:00 · Review

When is SOLID too much?

Ask the room

Where have you seen SOLID applied so eagerly that a 10-line script became five files? What was actually gained?

Ask tech leads

What's your team's real signal for "this needs an interface" — is it written down, or does it live in one person's head?

Ask QEs

Does an interface you can't easily fake in a test actually satisfy DIP, or does it just look like it does?

Ask AI engineers

An agent told to "make this more SOLID" will often add interfaces everywhere. When is that right, and when is it exactly the over-engineering this session warns about?

Before the room breaks, each person commits to one:

Find one class with more than one reason to change, and name both reasons
Find one place a concrete dependency is constructed inside a class instead of passed in
Delete one interface with exactly one implementation that will likely only ever have one
Bring one real "is this over-engineered?" example to raise with your team this week

Answer key — SubscriptionManager (one valid shape) 
class SubscriptionValidator:
    VALID_PLANS = ("monthly", "annual")

    def validate(self, plan):
        if plan not in self.VALID_PLANS:
            raise ValueError("unknown plan")

class SubscriptionPricing:
    PRICES = {"monthly": 29.00, "annual": 290.00}

    def price_for(self, plan):
        return self.PRICES[plan]

# subscription.mark_renewed() moves the state mutation onto the entity itself
class SubscriptionManager:
    def __init__(self, payment_gateway, email_service, validator, pricing):
        self.payment_gateway = payment_gateway
        self.email_service = email_service
        self.validator = validator
        self.pricing = pricing

    def renew(self, subscription, plan):
        self.validator.validate(plan)
        price = self.pricing.price_for(plan)
        self.payment_gateway.charge(subscription.customer_id, price)
        subscription.mark_renewed(plan)
        self.email_service.send_renewal_notice(subscription, plan, price)

A third plan is a new entry in PRICES and VALID_PLANS — not a new elif in renew(). That's the OCP payoff of splitting pricing out on its own.
