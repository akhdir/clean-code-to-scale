0:00–0:25 · Concept

Ports and adapters, by direction

Same dependency rule as Day 9, new vocabulary: which side of the core a port sits on determines who calls whom.

Driving side — calls in

  • The port describes what the outside world can ask the core to do
  • Adapters: HTTP controllers, CLI commands, test harnesses, message consumers
  • The adapter depends on the core; the core has no idea any of them exist

Driven side — calls out

  • The port describes what the core needs from the outside world
  • Adapters: database repositories, email/SMS senders, payment gateways, third-party APIs
  • Same dependency rule, opposite direction of data flow: the adapter still depends on the core's port
0:25–1:15 · Live demo

The same port, three adapters

Where Day 9 left off — one port (OrderRepository), one adapter (PostgresOrderRepository), one use case (PlaceOrder) that depends on the port, never the adapter. Today we add two more adapters live, and count how many lines of PlaceOrder change. The answer is the whole session.
Postgresproduction
class PostgresOrderRepository(
    OrderRepository
):
    def save(self, order):
        conn = psycopg2.connect(
            "dbname=orders"
        )
        cur = conn.cursor()
        cur.execute(
            "INSERT INTO orders "
            "(id, status) VALUES "
            "(%s, %s)",
            (order.id, order.status),
        )
        conn.commit()

From Day 9, unchanged. The real backend.

In-memorytests
class InMemoryOrderRepository(
    OrderRepository
):
    def __init__(self):
        self.orders = {}

    def save(self, order):
        self.orders[order.id] = (
            order
        )

No network, no database, no setup. Five lines.

Loggingproduction + audit
class LoggingOrderRepository(
    OrderRepository
):
    def __init__(self, wrapped, logger):
        self.wrapped = wrapped
        self.logger = logger

    def save(self, order):
        self.logger.info(
            f"saving {order.id}"
        )
        self.wrapped.save(order)

Wraps another adapter — doesn't replace it.

wiring — the only thing that changesPlaceOrder.run() is untouched
# production
place_order = PlaceOrder(PostgresOrderRepository())

# tests — no network, no database
place_order = PlaceOrder(InMemoryOrderRepository())

# production, with an audit trail — wraps the real adapter
place_order = PlaceOrder(
    LoggingOrderRepository(PostgresOrderRepository(), logger)
)

# PlaceOrder.run() never changes. Not one line, in any of the three.
Talking points
  1. PlaceOrder.run() is identical in all three lines above — same file, same method, zero edits.
  2. InMemoryOrderRepository turns a test that needed a running Postgres instance into one that runs in milliseconds with no setup.
  3. LoggingOrderRepository doesn't replace the Postgres adapter — it wraps it. Composition, not modification, because both sides only ever depend on the port.
  4. Whoever constructs PlaceOrder — a test, a script, your production entry point — decides which adapter to wire in. PlaceOrder itself never gets a vote.
1:15–1:45 · Hands-on

Define one port for your own service

Bring back your Day 9 diagram — specifically the violation you circled, or any item from your "Frameworks & Drivers" row. No diagram handy? Today's OrderRepository case study works fine to practice on instead.

Write a port, then one adapter for it
30 minSolo → pairs
TaskPick one concrete dependency from your own service. Write the port — only the methods your use case actually calls, named for what it needs, not for the technology behind it. Then write one adapter implementing it: real, or a fake built just for this exercise.
  • Look at the port you just wrote — does it describe what your use case needs, or does it leak details from one specific implementation (a method named after a SQL table, an argument shaped like an HTTP response)?
  • If you had five minutes to write a second adapter for this port — an in-memory fake, purely for tests — how many methods would you actually have to implement?
  • Which of your Day 9 "Frameworks & Drivers" items would benefit most from becoming a port? Which one is genuinely fine staying a direct dependency?
Done when
  • You have a port with 1–3 methods, named for what the use case needs, not the technology
  • You have one working or sketched adapter implementing it
  • You can state, in one sentence, what a second adapter would need to do differently
