Opening · 0:00–0:10

One Monday question

On Monday morning a product manager asks: "What was our revenue by customer segment last quarter?" It sounds simple. Here is what happens:

  • An engineer runs a big query on the orders database at 10:00. Checkout gets twice as slow for twenty minutes.
  • The number is wrong anyway. Refunds live in the Payments database, and segments live in the Customers service. Nothing joins them (Day 7).
  • The next week the same person asks for it by month, and for the last two years. Nobody kept the old values, because the database only stores the current state.

Three questions for today:

  1. Where should questions like this run, so that checkout never notices?
  2. How does the data get there, and how do we know it arrived once and in full?
  3. How do we trust the number?

  1. Ask: who has been asked for "a quick number" from production? What did you do, and what happened? Take two or three stories and refer back to them.
  2. Connect to Day 7: "what you lose for good" was the ad hoc join across services. Today is the answer.

Part 1 · 0:10–0:35

Two kinds of work

Databases do two very different jobs, and one machine is rarely good at both. OLTP (online transaction processing) runs the business: take an order, update a stock count. OLAP (online analytical processing) helps you understand the business: revenue by segment, returns by product.

OLTP (the application)OLAP (analytics)
PurposeRun the businessUnderstand the business
A typical queryGet, insert or update a few rows by keyScan millions of rows and add them up
Speed neededMilliseconds, with thousands at onceSeconds to minutes, with a few at once
Storage shapeRow by rowColumn by column
HistoryThe current state. Old values are overwrittenAll the history is kept
Used byCustomers and servicesAnalysts, dashboards, ML
ExamplesPostgres, MySQLBigQuery, Snowflake, Redshift, ClickHouse

Why not just run the report on production?

  • It competes with checkout. A big scan uses CPU, memory and disk that customers need. This is the shared resource from Day 4.
  • Long queries cause side effects. They slow cleanup in the database, and on a replica they can make it fall behind.
  • The schema is shaped for transactions, not for questions. It is split into many small tables, and the useful answer needs many joins.
  • The history is gone. If a customer moved to another country, all their old orders now show the new country.
  • No single database has the answer after the split on Day 7.
A read replica is a start, not an answer. It protects checkout from the load (Day 4), but it does not fix the schema, the missing history, or the data that lives in other services.

Row storage and column storage

An order database stores each order as a row, so reading one whole order is fast. An analytical question usually needs one or two columns from millions of rows, for example the amount of every order. A column store keeps each column together, so it reads only what the question needs, and it compresses well because similar values sit next to each other. Parquet is the common file format built this way.

Part 2 · 0:35–1:00

Warehouse, lake, lakehouse

Where should the analytical copy of the data live? There are three common answers. They are not rivals so much as three points on a line, from "tidy and ready to query" to "cheap and keep everything".

Data warehouseData lakeLakehouse
What it holdsCleaned, modelled tablesFiles of any kind: JSON, CSV, logs, images, ParquetLake files, organised as tables
SchemaDecided before loading (schema on write)Applied when you read (schema on read)A table format adds a schema to the files
StorageManaged by the warehouseCheap object storage (S3, GCS, Azure)Cheap object storage, plus a table format (Delta Lake, Iceberg, Hudi)
Good forDashboards, finance, SQL for everyoneRaw history, ML, data with no fixed shapeOne copy for both reports and ML, with updates and deletes
Watch out forNew messy sources need work before they can be loadedA "data swamp": nobody knows what is in it or which copy is rightNewer, with more moving parts
ExamplesBigQuery, Snowflake, RedshiftFiles on S3 read by Spark or AthenaDatabricks, or Iceberg on S3

Layers: raw, cleaned, modelled

Whichever you pick, good teams do not load data straight into the final tables. They keep it in layers, so that a mistake can be fixed by re-running from the layer below. A common naming is bronze, silver and gold.

Modelling for questions: the star schema

The top layer is shaped for questions. The classic shape is a star. In the middle is a fact table: one row per event, with numbers you add up (amount, quantity). Around it are dimension tables: the things you group and filter by (customer, product, date, region). The question "revenue by segment last quarter" becomes a simple join and a sum:

revenue by segment, last quarterone join per thing you group or filter by
SELECT c.segment, SUM(f.amount) AS revenue
FROM fact_orders f
JOIN dim_customer c ON c.customer_key = f.customer_key
JOIN dim_date d     ON d.date_key     = f.date_key
WHERE d.quarter = '2026-Q3'
GROUP BY c.segment

The snowflake schema

A variation of the star. In a star, each dimension is one wide table. In a snowflake, the dimensions are normalised: split into smaller, linked tables. The customer table no longer holds the country and region. It holds a geography_key, and a dim_geography table holds them. The product table holds a category_key, and a dim_category table holds the category name.

StarSnowflake
JoinsFewer, so queries are short and quickMore, so queries are longer and a little slower
Repeated dataSome: the category name sits on every product rowLittle: the category name is stored once
A changeUpdate many rowsUpdate one row
ReadabilityEasy for analystsHarder: more tables to know
Most teams start with a star. The simple shape is easier to use, and storage is cheap. Use a snowflake when a dimension is very large, or has a hierarchy that changes often. It is not related to the Snowflake company: the name comes from the shape of the diagram.

Keeping the history right

Remember the customer who moved country, and whose old orders suddenly show the new one? The fix is to keep both versions of the customer row, each with the dates it was true (often called a "type 2" slowly changing dimension):

customer_keycustomer_idsegmentvalid_fromvalid_to
10142standard2024-02-012026-05-31
87442premium2026-06-01(still true)

An order placed in April points at key 101, so it still counts as "standard". An order in July points at 874. Revenue by segment now matches what was true at the time.

Part 3 · 1:00–1:30

Moving the data

The anatomy of a data pipeline

Every pipeline has four stages, and four things around them that people forget.

StageWhat it does
IngestBrings the data in: change data capture, files, APIs, events
StoreLands it, raw, in the lake or warehouse
TransformCleans, joins and models it
ServeGives it to dashboards, ML models and APIs, and sometimes back into the application (reverse ETL)

Around them: orchestration (runs the steps in order, retries, backfills), quality checks (stop a bad load), lineage (where did this number come from?) and access control (who may see what). A pipeline without these four is a script that happens to run.

The data starts in the production database. How does it get to the warehouse without hurting the application, and without losing or repeating anything? There are four common ways:

WayHow it worksProblems
Nightly full copySELECT * from every table, every nightHeavy on production. Misses deleted rows. Nothing between two nights
Incremental by timestampCopy rows where updated_at is newer than the last runLighter, but misses deletes, and misses rows whose updated_at was not kept up to date
Change data capture (CDC)Read the database's own change log and send every insert, update and delete, in orderYou need a tool, and must handle the first full copy and schema changes
Events from the appThe service publishes business events (the outbox from Day 7)Best meaning, but the service team must build and maintain them

Change data capture, in a picture

Every database already writes every change to a log, so it can recover after a crash (in Postgres this is the write-ahead log). A CDC tool such as Debezium reads that log, so the queries on the database are not touched. It publishes each change to Kafka (Day 4), and from there it flows on to the lake or the warehouse.

One change event looks like this. It carries the old and the new row, what kind of change it was, and where in the log it came from:

a change event (simplified)one update to one row
{
  "op": "u",                                         # c = create, u = update, d = delete
  "before": { "order_id": 42, "status": "pending" },
  "after":  { "order_id": 42, "status": "paid" },
  "source": { "table": "orders", "lsn": 2318471 },   # the position in the log, usable as an event ID
  "ts_ms": 1790000000000
}

ETL or ELT: where does the cleaning happen?

ETL (extract, transform, load) cleans the data on the way in, before it reaches the warehouse. ELT loads the raw data first and transforms it inside the warehouse, usually with SQL (dbt is a common tool for this). Storage and compute are cheap now, and keeping the raw data means you can fix a bug in the logic and run it again.

Batch or streaming

BatchStreaming
HowProcess a chunk of data on a schedule (every night, every hour)Process each event as it arrives
DelayMinutes to hoursSeconds
ComplexitySimpler to build, test and re-runHarder: ordering, late data, state, restarts
Use whenDashboards, reports, daily financeFraud checks, live inventory, alerts
Do not stream what a nightly batch answers. Most dashboards need minutes or hours, not seconds. Ask the person who will read it how fresh it must be, and pick the simplest option that meets that.

Processing a stream: windows

A batch job has a file with an end: count all of it and you are done. A stream never ends, so when do you stop counting and give an answer? The answer is a window: a slice of time. Count the orders in each five-minute slice. Streaming is mostly about windows, about time, and about events that arrive out of order. There are three kinds of window:

WindowUse it for
TumblingOrders per five minutes, revenue per calendar day
Sliding (hopping)Average response time over the last 10 minutes, updated every minute. Alerts on "3 failures in 10 minutes"
SessionHow long a visitor stayed, ending after 30 minutes of silence

A window in a query

In code, a window is one extra idea on top of the SQL you already know. It is the same GROUP BY as in batch, but grouped by the window. Engines such as Flink, Spark Structured Streaming, Kafka Streams and ksqlDB all support this, and the exact syntax differs by engine.

orders per five minutes (simplified)one row per window
SELECT window_start,
       COUNT(*)    AS orders,
       SUM(amount) AS revenue
FROM orders
GROUP BY TUMBLE(order_time, INTERVAL '5' MINUTE)

Event time, watermarks and late events

There are two clocks. Event time is when it happened, on the phone. Processing time is when it reached the pipeline. They differ, and events arrive out of order. A watermark is the pipeline's guess: "I believe nothing older than this will arrive any more." Here the watermark is the newest event time minus 2 minutes, and we watch the window 12:00 to 12:05:

ArrivalEvent timeWatermarkWhat happens
112:0111:59The window is open. Counted
212:0312:01Still open. Counted
312:0612:04Belongs to the next window. Moves the watermark
412:04 (late)12:04Arrived after event 3, but the window is still open. Counted
512:0812:06The watermark passes 12:05. The window closes and its result is emitted
612:02 (too late)12:06The window is closed. Drop it, send it to a side output, or fix it later in batch
The trade-off. Wait longer and the result is more accurate but slower. Wait less and it is faster, but more late events are lost. Whatever is too late can be fixed by re-running the day from the raw data, which is another reason to keep it.

State and checkpoints

Counting per window needs memory: a count for every window and every key. This is state. If the job crashes the state is lost, and the count restarts from zero, which is a wrong number. The fix is checkpoints: every minute or so the engine saves a snapshot of the state and the Kafka offsets together, to a safe store. After a crash it restarts from the last checkpoint and replays from the saved offsets (the offset idea from Day 4).

Exactly-once is a team effort. Replaying means some events are processed twice. So the effect on the outside is exactly once only if the output is safe to repeat: an idempotent write, or a transactional one. Exactly-once effect is at-least-once delivery plus a sink that handles repeats. It is the same rule as the rest of the course.

Joins in a stream

The common case is enrichment: an order event has a customer_id and you want the segment.

  • The trap: calling the Customers database for every event. It is the N+1 problem from Day 7, now at stream speed, and it will melt the database.
  • Stream-table join: keep a local copy of the customers table inside the job, updated from the change data capture topic. Join each event to the copy. No remote call. For a small table you can also send a copy to every worker (a broadcast join).
  • Stream-stream join: for example, match a payment to its order. It needs a window: match them if they arrive within 30 minutes of each other.

Lambda architecture: two paths

Events go down two paths at once. The batch layer recomputes the answer from all the raw data, say every night. It is accurate, but slow: its results are hours old. The speed layer is a stream job that looks only at the newest events. It is fast, but approximate, because it has not seen everything and may not handle late events perfectly. The serving layer merges both when someone asks a question: the batch view covers everything up to last night, the real-time view covers what has happened since.

Kappa architecture: one path, and replay

Kappa removes the second path. There is only a stream job, and a Kafka log that keeps the events for a long time, so they can be read again from any offset. Normally job version 1 reads the newest events and keeps a table up to date. To fix a bug or change the logic, you start job version 2 with the new logic, and it replays the log from offset 0 into a new table, alongside version 1. When version 2 has caught up with the present, you switch queries to the new table and stop version 1.

Lambda, Kappa, or just micro-batch?

How it worksThe price
LambdaTwo paths: a batch path (accurate, slow) and a speed path (fast, approximate), merged when servingTwo code bases that must give the same answer
KappaOne streaming path. To reprocess, replay the log from the startNeeds a log that keeps the data long enough, and state you can rebuild
Micro-batchPlain batch, every few minutes (for example every 5)A delay of minutes, but easy to build, test and re-run
Pick the simplest option that meets the freshness the reader needs. Many dashboards are fine with a batch every five minutes.

Five failures you will meet in streaming

Most of them are old friends from Day 4.

FailureWhat happens, and what to do
BackpressureThe consumer is slower than the producer, and lag grows. Add partitions and consumers. Alert on lag
Bad recordsOne message always fails and blocks the partition. Retry a few times, then dead-letter it
SkewOne key sends most of the traffic, and one partition is a hot spot. Add a random part to the key
Schema driftA producer changes a field. Use a contract and a schema check at the boundary
ReprocessingYou fixed a bug and need to redo the past. Replay from the log, into a sink that is safe to repeat

Which window?

For each need, pick a window: tumbling, sliding or session.

  1. Orders per five minutes, shown on a dashboard.
  2. Average response time over the last 10 minutes, updated every minute.
  3. How long a visitor stays, ending after 30 minutes of silence.
  4. Alert when one card has 3 failed payments within 10 minutes.
  5. Revenue per calendar day.
Show the answer
  1. Tumbling. A fixed slice, no overlap.
  2. Sliding. A rolling look back, updated every minute.
  3. Session. It follows the visitor's burst of activity and closes after a gap.
  4. Sliding. The 10 minutes must roll, so a burst across a boundary is not missed.
  5. Tumbling. One window per calendar day.

The test: a fixed calendar slice is tumbling. A rolling look back is sliding. Bursts of activity are session.

Running it, and running it again

Pipelines are many steps with dependencies: load, clean, model, then check. An orchestrator (Airflow, Dagster, Prefect) runs them in the right order, on a schedule, retries failed steps, and lets you backfill, which means re-running the past for a range of days after fixing a bug. Backfills only work if each step is safe to run twice. This is the idempotent consumer from Day 4, in a new place:

load_orders.py — appenda retry doubles the revenue
def load_orders(day):
    rows = read_raw("orders", day)
    append("fact_orders", rows)                  # run it twice and every order is counted twice
load_orders.py — replace the daysafe to run again
def load_orders(day):
    rows = read_raw("orders", day)
    rows = dedupe(rows, key="event_id")          # the same event twice becomes one
    overwrite_partition("fact_orders", day, rows)   # replace the whole day, never append
The rule: replace the day, never append to it. Then a retry, a restart and a backfill all give the same result.
Part 4 · 1:30–2:00

Trusting the data

When a service breaks, you get an error and an alert. When a pipeline breaks, you often get a number that is quietly wrong, and a decision made on it. Trust has to be built in.

Checks that stop a bad load

CheckWhat it asksIt catches
FreshnessDid the newest data arrive on time?A stuck pipeline, and a dashboard showing yesterday
VolumeIs the row count close to normal?A half-loaded day, or a double load
UniquenessDoes any key appear twice?Duplicates and double counting
CompletenessAre required fields filled?A renamed field that arrives empty
ValidityAre values in range (amount above zero, known status)?Bad inputs and wrong units
ReconciliationDoes the total match the source?Lost rows between the source and the warehouse
checks.sql — the pipeline stops if any of these returns a rowrun after every load
-- uniqueness
SELECT order_id FROM fact_orders GROUP BY order_id HAVING COUNT(*) > 1;

-- volume: fewer than 1,000 rows for the day is wrong
SELECT 1 FROM fact_orders WHERE order_date = '2026-10-07' HAVING COUNT(*) < 1000;

-- freshness: nothing newer than 30 minutes
SELECT 1 FROM fact_orders HAVING MAX(loaded_at) < NOW() - INTERVAL '30 minutes';

Contracts: when the source changes

The Orders team renames amount to total. The service still works, and the dashboard column goes empty. This is the Day 7 contract problem, on the data side. The fix is the same: the producer publishes a schema (a schema registry with Avro or Protobuf is a common way), and a change that would break a consumer fails the producer's build.

Change to a fieldBreaks the pipeline?
Add an optional fieldNo
Rename a fieldYes. Add the new name, keep the old for a while, then remove it
Change a type (number to text)Yes
Remove a fieldYes, if anyone still reads it
A new value for a fixed list (a new status)Maybe. Check anything that sorts or filters on the list

Lineage: where did this number come from?

Lineage is the chain from a number on a dashboard back to its source. For our revenue tile it looks like this, and you trace it from right to left:

  • Find the source of a wrong number: follow the chain back until it breaks.
  • Impact analysis: before you rename a field, see what depends on it. This is the contract problem again.
  • Privacy: see where personal data goes, so that a delete can follow it.

Tools such as OpenLineage, dbt docs and data catalogs record this for you. Also give every table an owner and a freshness promise, so that someone is responsible for it.

Duplicates and late data

At-least-once delivery (Day 4) means the same event can arrive twice, so every pipeline needs a key to dedupe on. Events also arrive late: a phone was offline, and its order reaches the pipeline two days after it was placed. Two rules:

  • Group by event time (when it happened), not processing time (when it arrived). Otherwise Tuesday's revenue changes depending on when the phone reconnects.
  • Allow for late data: when a late event arrives, re-run the day it belongs to. This is why the pipeline must be safe to run again.

Personal data

Copying data into a lake also copies its personal information (names, emails, addresses) into a place with many more readers. A "delete me" request now has to reach every copy. Habits that help (this is engineering guidance, not legal advice):

  • Copy less. Do not send fields nobody will ever ask about.
  • Separate it. Keep personal fields in one small, tightly controlled table, and use a customer ID everywhere else.
  • Control access by column and by role, and log who reads what.
  • Make deletes travel. Send delete events (CDC does this), and use a table format that supports row-level deletes (Iceberg, Delta). Keep a record of what was deleted and when.
Quiz · 4 min

What went wrong?

Four incidents. For each, say what most likely went wrong, and which check or habit would have caught it.

  1. On Monday the revenue dashboard shows exactly double the usual number. The pipeline failed on Sunday night and was retried.
  2. At 3 pm the dashboard still shows yesterday's numbers, and nobody was told.
  3. A customer asked to be deleted last month, and still appears in a report.
  4. After a release, the "amount" column on the dashboard is empty.
Show the answer
  1. The load appends, so the retry added the day twice. Replace the day instead of appending, and a uniqueness or volume check would have stopped it.
  2. No freshness check. The pipeline was stuck or late, and nothing compared the newest data to the clock. Alert when the newest row is older than the limit.
  3. Deletes did not travel. A nightly copy misses deleted rows, and the lake kept the old files. Use CDC delete events and a table format with row-level deletes.
  4. A schema change with no contract. A field was renamed at the source. A completeness check (null count) would have caught it, and a schema check would have stopped the release.

Every one of these is a silent failure: nothing crashed. That is why the checks are a part of the pipeline, not an extra.

Answer key — Exercise B (checkout to dashboard)

There is no single right answer. A good one looks like this:

  • How data leaves: change data capture. A tool reads the Postgres change log and publishes every insert, update and delete to Kafka, one topic per table. Checkout runs no extra query. A nightly copy fails the 15-minute refresh, misses deletes, and loads production. A timestamp-based copy misses deletes too, and trusts updated_at.
  • Where it lands: the raw layer of the lake or warehouse, append only, partitioned by date. Then a cleaned layer (deduplicated by event ID), then the modelled layer: fact_orders (amount, quantity) with dim_customer (segment, as a type-2 dimension so history stays right), dim_date, dim_product.
  • Re-running a bad day: every load replaces the partition for the day it covers (or merges on the event ID). Fix the bug, re-run the day, and the result is the same however many times it runs. Late events re-run the day they belong to.
  • Two checks that stop a bad load: freshness (the newest row is less than 30 minutes old) and uniqueness of order_id. Volume against the source (the count matches within about 1%) is a strong third.
  • Personal data: the lake and the facts carry only customer_id. Name and email live in one small, access-controlled table. A delete in the source arrives as a CDC delete event, and removes the person from that table. A table format with row-level deletes removes it from the history within the 30 days. The dashboard only ever sees the segment.

Look for: a pair that says "run a nightly query on a replica". That protects checkout, but it fails the 15-minute refresh, the history, and the delete. Ask what each requirement rules out.

Talking points
  1. An analytical question and a customer's click are different jobs. Giving them different machines is not waste, it is what lets both be fast.
  2. Keep the raw data. Almost every pipeline bug is fixed by running the corrected logic again, and that needs the original input.
  3. Days 4 and 7 return here: events need IDs, consumers must be safe to run twice, and a contract at each boundary keeps the other side from breaking.
  4. A wrong number that looks right is the worst failure a data system has, because nobody is alerted. Build the checks first.
