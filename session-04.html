Part 1 · 0:00–0:55

Scaling web and API requests

Web servers are the easiest part of a system to scale out, if three things are true: the servers keep no data about users, you chose on purpose where sessions are stored, and a thousand requests never wait in line for one database row.

Three ways to scale, one requirement

There are three ways to scale. Each has tradeoffs. Only one is easy to add more of, and it has a requirement the others don't.

Vertical — scale up

  • A bigger machine. No code changes, so it is the easiest option
  • There is a limit: the biggest machine you can buy
  • One machine is one point of failure

Horizontal — scale out

  • More machines running the same code, behind a load balancer
  • Cheap and close to linear at first, but it needs stateless servers, and the gains shrink later (see the curves below)
  • Backup comes free: if one server dies, the others keep working

Functional — split by responsibility

  • Break a big application into parts, so each part can scale on its own
  • Contains failures: one overloaded part does not take down the rest
  • Function calls become network calls. That is Day 7's whole topic

Stateless vs. stateful

The requirement is statelessness: a server does not remember a user between two requests. The system still has state. It just lives somewhere other than the web servers.

Stateful instanceStateless instance
Where a user's data livesIn this server's memory, such as a cart or session objectIn a shared store (Redis, the database) or inside the request itself
Which instance can answerOnly the server that holds the dataAny of them
An instance diesEvery user on it loses their session and cartNothing is lost. The load balancer sends traffic to other servers
Autoscale or deployUsers get logged out, and servers cannot be removed freelyServers are disposable. Users do not notice scaling

Session handling: three ways to remember a user

Login state and shopping carts have to be stored somewhere. There are three common choices. Each is a tradeoff, not a "best practice".

Why sticky sessions cause trouble
  1. Uneven load. A few heavy users stuck to one server can overload it while other servers sit idle, and the load balancer cannot move them.
  2. When a server dies, its sessions die. Every user stuck to it is logged out or loses their cart, in the middle of the sale.
  3. Deploys and autoscaling get harder. To remove a server you must wait for its sessions to end, or log those users out.
  4. IP-based routing misleads. Thousands of people behind one company network share one IP address, so they all land on the same server.
  5. It hides the bug. A stateful app looks fine behind sticky routing in testing and normal traffic, until a server is replaced under load.

Why nine instances made it worse, not better
  1. Request 1 (add to cart) goes to server A. Now A's carts memory holds this customer's item.
  2. Request 2 (view cart) goes to server C. The load balancer does not know request 1 happened, and C's carts is empty for this customer.
  3. The bug was always there. With one server, the same server always answered both requests, so nobody saw it.
checkout_service.py — statelesscart lives in Redis, not in the process
def add_to_cart(session_id, item):
    redis.rpush(f"cart:{session_id}", item)

def get_cart(session_id):
    return redis.lrange(f"cart:{session_id}", 0, -1)
Talking points
  1. Same two functions, same callers. Only the place where the state lives changed. That is usually true: making an app stateless is a storage decision, not a rewrite.
  2. Now any of the nine servers can answer either request, because none of them holds the data. Redis does.
  3. One more cheap fix that is easy to miss: the product-price lookup hit the database on every cart action. A cache in front of it (the Cache box in the diagram) reduces database load without adding a single server.
  4. Sticky sessions would have hidden this bug. Each customer keeps going to the server with their cart, so it works, until that server is replaced mid-sale and all those carts disappear at once.

1,000 requests, one row

Stateless servers can be multiplied freely, until they all need to change the same thing. In a flash sale on one product, every buyer must lower the same stock number.

buy.py — beforethe row lock is held across a slow call
def buy(product_id, user_id):
    with db.transaction():
        row = db.query_one(
            "SELECT stock, price FROM products WHERE id = %s FOR UPDATE",
            product_id,
        )                                          # row lock taken here...
        if row.stock < 1:
            raise SoldOut()

        payment_api.charge(user_id, row.price)     # ...and held through a ~200 ms network call

        db.execute("UPDATE products SET stock = stock - 1 WHERE id = %s", product_id)
        db.execute("INSERT INTO orders (user_id, product_id) VALUES (%s, %s)", user_id, product_id)

The lock exists for a good reason: two buyers must not both get the last item. But a lock turns "many requests at once" into "one request at a time". For this row, the whole system runs one by one, and its speed has nothing to do with how many servers you have:

Speed on a hot row is 1 / time the lock is held. Nine servers or ninety, the same five buyers per second get through. The others are not idle. They are waiting, and waiting costs something:

0 s

The sale opens. 1,000 buy requests arrive across 9 servers. One gets the row lock and 999 wait. Each waiting request holds a thread and a database connection.

2 s

The connection pool fills up (say it holds 100). Now requests that have nothing to do with the sale, like browsing, login and the cart, cannot get a connection either. The whole site slows down, not just the buy button.

5 s

Timeouts cause retries. Clients and the load balancer give up and try again. But the old requests are still running on the server, waiting for the same lock. Every retry adds another waiting request instead of removing one.

10 s

Health checks start failing (they use the database too). The load balancer removes "unhealthy" servers, so the remaining ones get more load and fail faster.

15 s

The failure spreads. Every service that calls checkout is now stuck waiting for an answer that never comes. This is the cascade Day 7 studies, and here one hot row started it.

# at pool setup, once per connection:  SET lock_timeout = '300ms'  -- wait briefly, then fail fast

Optimistic locking, up close

A lock is pessimistic: it assumes someone will interfere, so it blocks everyone first. Optimistic locking assumes nobody will, so it works first and checks at the end that nobody changed the row. The check uses a version column.

buy.py — optimistic versionno lock; check the version when saving
def buy(product_id, user_id):
    for attempt in range(3):
        row = db.query_one(
            "SELECT stock, version FROM products WHERE id = %s", product_id)
        if row.stock < 1:
            raise SoldOut()

        updated = db.execute(
            "UPDATE products SET stock = stock - 1, version = version + 1 "
            "WHERE id = %s AND version = %s",
            product_id, row.version)
        if updated == 1:
            return          # nobody else changed it: done
        # 0 rows changed: someone got there first, so read again and retry
    raise TryAgainLater()

Read the row and remember its version. Do your work with no lock held. Update only if the version is still the same. If nothing was updated, someone else won, so read again and retry a limited number of times.

This is great when conflicts are rare. On a hot row it backfires, because only one buyer wins each round and everyone else repeats the work:

Does 2× the machines give 2× the work?

Every way of scaling is judged by one question: if I add more machines, how much more work gets done? Scaling out promises the best answer: double the machines, double the work. This ratio is called speedup: how many times more work per second N machines do compared with one machine. Perfect scaling means speedup = N.

Your checkout servers are close to this best case. Every request is independent, so doubling the servers roughly doubles the requests handled per second. That holds until the servers depend on something they share, like the hot row you just saw. That shared thing is the whole story of this section, and it breaks the straight line in two ways:

1. Work that can't be split

  • Some step must happen one at a time, in order, on one machine, such as a lock, a final summary write, or a single main database
  • Engineers call this the serial part. Extra machines cannot speed it up, no matter how many you add

2. Machines having to talk

  • Machines that share data must coordinate: clear each other's caches, agree on a lock, copy a write
  • This talking takes time, and it grows with every machine you add

We put numbers on this in Part 2, using a nightly job.

Scaling backend jobs with queues

Not all work is a web request. Nightly jobs, emails and reports run in the background. First we see how much extra machines really help a job. Then we see how a queue hands the work out.

A nightly job: one machine, then many

Let's see "work that can't be split" in real code. A nightly job recalculates every customer's loyalty tier and then writes the results to one summary table. On a single machine it takes 100 minutes:

loyalty_job.py — one machine100 minutes, start to finish
def recalculate_loyalty_tiers(customers):
    tiers = {}

    # part 1: per-customer work — every customer is independent of every other
    for customer in customers:
        tiers[customer.id] = compute_tier(customer.orders)   # ~95 min, all customers

    # part 2: the summary write — one table, one lock, one writer at a time
    with summary_table.lock():
        summary_table.write_all(tiers)                       # ~5 min
        summary_table.write_totals(tiers)                    # needs every tier first

Part 1 is easy to share out: customer 7's tier does not depend on customer 8's, so ten machines can each take a tenth of the customers. Part 2 cannot be shared out: the totals need every tier first, and the table lets only one writer in at a time. Now split the job across N machines:

loyalty_job.py — N machinespart 1 shrinks, part 2 doesn't
def tier_chunk(chunk):                                       # runs on every machine at once
    return {c.id: compute_tier(c.orders) for c in chunk}

def recalculate_loyalty_tiers(customers, machines):
    chunks = split(customers, parts=len(machines))
    partials = run_on_each(machines, tier_chunk, chunks)     # ~95 / N min
    tiers = merge(partials)

    with summary_table.lock():                               # still one writer
        summary_table.write_all(tiers)                       # still ~5 min
        summary_table.write_totals(tiers)
Total time = 95 / N + 5 minutes. With 4 machines: 23.75 + 5 = 28.75 minutes. With 20: 4.75 + 5 = 9.75. With 1,000: 0.095 + 5, about 5.1. The 5 never changes; only the 95 gets smaller. In the code above, run_on_each(machines, tier_chunk, chunks) quietly handed each chunk to a machine. In a real system, something must hand each chunk to a machine, notice when one dies, and never lose or repeat a chunk. That something is a queue. Queues are not only for batch jobs. They are the standard answer for any work that does not need to finish before the customer gets a reply.

Why put a queue in the middle

checkout.py — beforethe customer waits for every step
def place_order(order):
    save_order(order)
    send_receipt_email(order)        # ~300 ms, third party
    update_loyalty_points(order)     # ~150 ms
    notify_warehouse(order)          # ~400 ms
    return "ok"                      # ~850 ms later — and a failure in any step fails the order
checkout.py — afterpublish one message, return
def place_order(order):
    save_order(order)
    queue.publish("order-placed", {"order_id": order.id})    # ~2 ms
    return "ok"

# on any number of worker machines, running separately
def loyalty_worker():
    for message in queue.consume("order-placed"):
        update_loyalty_points(message["order_id"])

Separates timing

  • The request returns when the work is accepted, not when it is finished
  • A slow email provider no longer slows down checkout

Absorbs spikes

  • A burst of orders becomes a backlog that workers clear at their own pace
  • Workers run at a steady load instead of the traffic peak

Fails and scales on its own

  • A crashed worker does not fail the order; its message goes to another worker
  • Add workers without touching the web servers

Day 3's Observer pattern was this same idea inside one program: the sender does not know who reacts. A queue is Observer across programs, and it adds durability and some new problems.

A queue absorbs spikes, not constant overload. If 6,000 messages arrive per second and workers finish 800, the backlog grows by 5,200 every second, over three million messages in ten minutes. The queue did not remove the waiting; it only moved it somewhere safer. You still need to add workers, drop load at the source, or accept a delay that keeps growing.

More workers on one queue

The first step is the obvious one: run more workers on the same queue. Each message goes to exactly one worker, so speed grows with the number of workers. This is the same "any server will do" idea from Part 1, applied to jobs. It stops being enough for two reasons. A single queue still runs on a single machine. And when order matters (for example, two updates to the same customer), several workers pulling from one line can no longer keep the order.

Splitting the queue: partitions

To scale the queue itself, split it. Instead of one line there are P separate lines (partitions), possibly on different machines. The sender picks a partition for each message by hashing a key (the same hash-the-key idea Part 3 uses to split a database). Every message with the same key goes to the same partition, in order. One consumer reads each partition at a time. Speed now grows with P, and order is kept, but only inside a partition.

Kafka: a queue split into partitions

A log, not a queue

  • Messages are added to the end and kept (for a set time or size), not deleted when read
  • A consumer just remembers its position (offset). It can go back and replay
  • Several consumer groups can read the same topic independently (loyalty, analytics, search)

Order and parallelism

  • Key, then hash, then partition: the same key always goes to the same partition, in order
  • Order is guaranteed only inside one partition, never across partitions
  • Number of partitions = the most consumers that can work in parallel in a group

Surviving failures

  • Each partition is copied to other servers. One copy leads and the rest follow
  • acks=all waits until the in-sync copies have the message before confirming the write
  • A group coordinator hands out partitions again when a consumer joins or dies (a rebalance)

Scaling the database

Web servers and workers are copies of code, so they multiply easily. The database holds the one thing that cannot be copied freely: the data. There are three steps, each bigger than the last: copy it, let every copy accept writes, or split it. The CAP theorem describes what each step gives up when the network has problems.

Step 1: primary and replicas (master–slave)

One server, the primary, accepts every write and sends its changes to one or more replicas. Reads can go to any of them. (Older docs say master and slave.) It is the cheapest way to scale a read-heavy service, needs no schema change, and gives you failover: if the primary dies, a replica can take over. What it cannot do is scale writes: there is still only one writer.

Replication modeWrite is confirmed when…StrengthTradeoff
Asynchronousthe primary has itFast writes. A slow replica never blocks anyoneReplicas fall behind. If the primary crashes, the last few writes that were not sent yet can be lost
Synchronousthe replica has it tooNo confirmed write is lost on failoverEvery write waits for the replica, and a down replica can stall writes
Semi-synchronousat least one replica has itA middle path used by many real systemsSlower than async, and limited by the slowest chosen replica

Failover has its own danger. If the old primary is only unreachable, not dead, and a replica takes over anyway, you now have two servers that both think they are the writer. This is called "split brain". Real systems block the old primary from accepting writes. And here is a common problem with async replicas, which the team hit three weeks after adding them:

orders.py — beforeevery read hits a random replica
def get_order_confirmation(order_id):
    return db.read_replica().get_order(order_id)
What actually happened
  1. A customer updates their shipping address at checkout. This is a write, and it goes straight to the primary.
  2. A split second later the confirmation page reads the order back. This read goes to whichever replica the load balancer picks.
  3. Replication delay is normally a few tens of milliseconds. This time it was enough: the replica still had the old address. The customer saw it and thought the site had undone their change.
orders.py — aftera read that follows its own write goes to the primary
def get_order_confirmation(order_id, session):
    if session.wrote_recently(order_id):
        return db.primary().get_order(order_id)
    return db.read_replica().get_order(order_id)
Talking points
  1. This is not a network partition, because nothing was unreachable (that is the CAP case, at the end of this part). It is replication lag: a small, constant delay that shows up exactly when a user reads back what they just wrote.
  2. The fix: only reads that follow the user's own recent write go to the primary. Sending every read there would remove the reason for having replicas.
  3. This is the cost of using read replicas. It is real, but specific and fixable. It is not a reason to avoid replicas.

Step 3: partitioning (sharding) — split the data

Replicas copy all the data, and multi-master copies the conflicts too. To scale writes and storage without conflicts, give each server only part of the data, and give each row exactly one home. Splitting a database carelessly is its own trap.

Partitioning in short. Partitioning means splitting data into pieces. Sharding is when the pieces live on separate database servers. (Splitting by columns or by feature is vertical partitioning. Here we mean splitting rows.) Instead of one orders table on one machine, you have four smaller orders tables on four machines, each a full database on its own. Every read and write must go to the one shard that holds the row, and your application (or a routing layer in front of it) now has to do that routing. The hard part is not the splitting. It is deciding, consistently, which row goes to which shard. The rest of this section is about that.

Mod hashing: simple, until N changes

The obvious way to pick a shard: turn the key into a number with a hash function, then take that number modulo the number of shards. hash("order_8842") might give a big number; with 4 shards, that_number % 4 gives 0 to 3, which is the shard. It is fast, needs no lookup table, and spreads keys evenly if the hash function is good.

The catch is inside the formula: N, the number of shards, is an input. Change N and the answer changes for almost every key, not just the new ones. Here are the same 8 keys with mod 4 and mod 5:

Consistent hashing: adding a shard moves few keys

Forget the number of shards for a moment and picture a clock. This clock has thousands of positions instead of 12, but the idea is the same. Instead of hours, it holds shards. Hash each shard's name to find where it sits on the clock face:

shard Asits at 2 o'clock
shard Bsits at 5 o'clock
shard Csits at 8 o'clock
shard Dsits at 11 o'clock

Now hash a key the same way: order_8842 lands at 3 o'clock. The rule is simple: walk clockwise until you reach a shard. From 3 o'clock the next shard is B at 5 o'clock, so order_8842 lives on B. No modulo, and no shard count anywhere in the rule.

Here is the payoff. Add a 5th shard, E, at 9 o'clock, between C (8) and D (11). order_8842 at 3 o'clock does not care. It still walks to B at 5. A, B, C and D did not move, because their positions never depended on each other. Only keys between 8 and 9 o'clock notice. They used to walk all the way to D at 11, and now they stop earlier, at E. Everyone else's walk is unchanged.

These steps work together, they do not compete. Distributed systems and the CAP theorem

The steps above each gained something by giving something up. This section asks why, from the beginning: what a distributed system is, what happens when its network splits, the CAP theorem, how to choose between the two answers it leaves you, and what "eventually consistent" means in practice.

What is a distributed system?

A distributed system is many computers that work together by sending messages to each other, and look like one system to the user. Your shop already is one: a load balancer, web servers, a cache, a primary and a replica, and Kafka.

Why we build themWhat it costs

Service A calls Service B and waits. Nothing comes back. Three things could have happened, and from where A sits they all look the same: silence, then a timeout.

So A cannot simply retry or give up. If it retries, the work may happen twice (this is why Part 2 insisted on safe retries). If it gives up, the work may already be done. Everything below grows from this.

Network partition: every node is up, but they can't talk

A network partition is when the network splits the nodes into groups that cannot talk to each other. No machine has to crash. The usual causes are boring: a switch or router fails, a link between cloud zones is cut, a firewall or config change, a busy link drops messages, or a long pause makes a node look dead. The dangerous part is that each group thinks the other group died, and carries on alone.

Split brain: two leaders, one set of data

A bank account has 100. A leader accepts writes and a replica copies them. Then the network is cut:

Normal

The replica copies every change from the leader. Only the leader accepts writes. Both show balance 100.

Cut

Each side thinks the other is down. The replica hears nothing from the leader, so it decides the leader is dead and promotes itself. The old leader hears nothing from the replica, so it thinks the replica is dead and carries on. Now there are two leaders. Client 1 withdraws 80 on one side; Client 2 withdraws 80 on the other. Both succeed. Both show balance 20.

Healed

The two copies have the same number but a different history. 160 was paid out of 100, and one withdrawal may have to be undone.

Split brain: each side believes the other is down, so both act as the leader, both accept writes, and the data drifts apart. "Just detect it faster" does not work: detection cannot tell a dead node from a cut link.

Stopping split brain: the majority rules

The fix is a majority. Take five nodes, split 3 and 2:

  • A leader needs votes from more than half of all nodes (3 of 5). Two groups can never both have a majority, so there is only ever one leader.
  • Use an odd number of nodes, 3 or 5, so a split cannot be even.
  • Fencing: each leader gets a number, and storage rejects writes carrying an older number, so a stale leader cannot do harm.
Look at the cost. The minority side stopped answering. We gave up availability to keep the data correct. That is exactly the CAP choice.

When a follower goes down: what happens?

A follower is any node that is not the leader. Take five nodes where N1 is the leader and N4 crashes.

  1. A follower crashes. The leader stops getting replies from N4 and keeps going. There is no election, because the leader is fine.
  2. Writes still work. A write needs a majority, 3 of 5. The leader plus N2, N3 and N5 is four, so the write is confirmed. The user notices nothing.
  3. N4 comes back and catches up. It restarts as a follower. The leader sends it the writes it missed (or a snapshot, if it was gone a long time), and it is a full member again.

When the leader goes down: how a new one is chosen

This is the idea in Raft, used by etcd, Consul and Kafka's KRaft (ZooKeeper uses a similar protocol). Take five nodes, N1 to N5, where N1 is the leader.

  1. Normal. The leader sends a short heartbeat every ~50 ms: "I am alive, I am still the leader."
  2. The leader crashes. The heartbeats stop. Each follower waits a different, random time (say 150 to 300 ms) before it decides the leader is gone.
  3. One timer runs out first, say N3's. N3 adds 1 to the term number (now term 2), votes for itself, and asks everyone: vote for me? Each node votes once per term.
  4. A majority says yes. N3 gets two more votes. That is 3 of 5, a majority. N3 is the leader of term 2 and starts sending heartbeats.
Notice the quorum. N3 needs more than half of all five nodes, not just the ones it can see. If the network splits 3 and 2, only the side with 3 can elect a leader. That is exactly what stops two leaders.

The CAP theorem: three properties

Eric Brewer proposed it in 2000, and Gilbert and Lynch proved it in 2002.

PropertyWhat it meansExample
ConsistencyEvery read sees the latest writeYou transfer 50. Your phone and your partner's phone both show the new balance straight away
AvailabilityEvery request to a working node gets an answer, not an errorThe ATM always answers, even if the answer is a little old
Partition toleranceThe system keeps working when messages between nodes are lostCairo and Dublin cannot reach each other, and both keep running
The theorem: when a network partition happens, a system cannot be both consistent and available. CAP's "consistency" is not the C in ACID.

Why you can't have all three: one lost message

Two nodes keep a copy of x. The client writes to Node 1, and Node 1 tells Node 2. Then the network between the nodes is cut, and the client asks Node 2 for x.

Why only two of three: CP, AP or CA

The network will fail sometimes, so partition tolerance is not a choice. The real choice is consistency or availability.

ChoiceWhat you give upExamples
CP: refuse when unsureAvailability. Some requests fail during a partitionBank transfer, seat 14C, etcd, ZooKeeper, a database where all reads go to the primary
AP: answer, fix laterConsistency. Answers may be old until the copies catch upLike count, shopping cart, DNS, Cassandra, DynamoDB (default reads)
CA: only on one machineThere is no network to split, so no partition to survive. It is not a distributed systemOne Postgres server with no replicas. Add a second machine and you must pick CP or AP

How to choose: AP or CP?

Ask what a wrong answer costs, and what a refusal costs. The business already has an opinion. Three questions, in order:

  1. Is an old or wrong answer dangerous? Money, safety, double booking, a unique name. If yes, choose CP.
  2. If two sides disagree, can you fix it later? By merging, last write wins, or a person reviewing. If no, choose CP.
  3. Does refusing cost more than a slightly old answer? Lost sales, blank pages, angry users. If yes, choose AP.

If the answer to all three is no, either works. Pick the simpler one. CP means: refuse or wait when unsure, use one leader, a quorum or consensus, and accept errors during a partition. AP means: keep answering with what you have, use replicas that catch up, merge rules and safe retries, accept old data for a while, and plan for conflicts.

  4. Refuse. Selling the same seat twice is worse than asking one customer to try again.

The right answer depends on what it costs to be wrong. That is a business question, not a technical one.

How a failure spreads

Everything so far assumed one thing breaks at a time. Real outages spread. A database gets slow, not dead. The inventory service waits on it, the orders service waits on inventory, and the web tier waits on orders. The slowness travels back toward the user, against the direction of the requests.

How it spreadsWhat happens
WaitingA slow service holds its callers' threads and connections. Slow is worse than down: a down service fails fast, a slow one ties everyone up
RetriesEach retry is more load on a service that is already struggling, so it gets slower, so more calls time out, so there are more retries
Shared resourcesOne connection pool, CPU or database serves many callers. One busy caller can starve all the others
Shared fateSame deploy, same zone, same config. One bad change breaks many services at once

Dissecting a cascading failure

One of four inventory servers crashes at 12:00. Twenty-five minutes later the whole shop is down. Read the timeline and find the minute when "one server crashed" turned into "the shop is down".

12:00

Trigger. One of four inventory servers crashes (a memory leak). The other three now carry 33% more traffic each.

12:02

Slow, not down. The three left run at 95% CPU. Replies slow from 80 ms to 900 ms. Callers keep waiting instead of failing.

12:03

Amplifier. The Orders API gives up after 1 second and retries, up to 3 times. Traffic to inventory is now about 3 times higher.

12:05

The failure moves up. All Orders API threads are stuck waiting. It stops answering health checks, so the load balancer removes it, and the remaining Orders servers get even more traffic.

12:10

Recovery trap. The team restarts the crashed server and adds new ones. They start with empty caches and meet the full retry backlog, so they fall over too.

12:25

Recovery. The shop comes back only after traffic is cut at the load balancer and retries are turned off. While the load stayed high, the system could not heal itself.

Part of the incidentWhat it was here
TriggerOne server out of four crashes. A normal event that the system should survive. It removed only 25% of capacity
AmplifiersRetries multiplied the load. Waiting threads filled up. Health checks removed slow servers, so capacity shrank. New servers started with empty caches
Recovery trapThe retry backlog hit every new server. The overload kept itself going, even after the trigger was gone. Teams call this a metastable failure

Breaking the chain: one defence for each step

Step in the incidentDefenceHow it works
Callers wait for a slow serviceShort timeoutsGive the whole request a time budget (for example 1 s). Pass what is left to the next call
Retries triple the loadRetry budget, backoff, jitterRetry only if retries are under about 10% of calls. Wait longer each time, with a random delay
A slow service keeps getting calledCircuit breakerAfter a number of failures, stop calling for 30 s and return a fallback instead
Overload makes everything slowLoad sheddingReject the extra requests early (HTTP 429 or 503) so the rest finish. Keep checkout, drop browsing first
One busy caller starves the restBulkheadsSeparate thread and connection pools for each dependency, so one cannot use them all
New servers fall over when they startSlow startSend a trickle of traffic to new servers and ramp up while their caches warm
The system cannot recover by itselfA kill switchA flag to turn off retries and optional features, so people can cut the load fast
If you could add only one before the next big sale, make it timeouts. Most of the other defences need them to work.
Talking points
  1. Each step gains something by giving up something: replicas give up freshness, multi-master gives up agreement, partitioning gives up simple queries. CAP is the same list, for the moment the network breaks.
  2. "Which one should we use?" is the wrong first question. Ask what your service does if a user sees old data, and what it does if it refuses a write. The business already has an opinion, and that picks the row in the table.
  3. Failures spread through waiting, retries, shared resources and shared fate. In the incident, the crash was small. The retries made it big. Ask the room where their own system multiplies work when something is slow.
  4. No design here makes the problem disappear. Each one only moves it. That is why the capacity plan in the next block starts by asking where your service's shared resource is.

Reference — the worked example, restated

Checkout handles 800 req/s comfortably today. A flash sale in six months is expected to push that to 2,400 req/s. Load testing shows one server handles 750 req/s before CPU passes 70%. 2400 / 750 = 3.2, rounded up to 4 servers for the load, plus 1 more so the system survives one server failing: 5 in total. None of this matters until the cart's state moves out of memory and into Redis, which is why that fix comes first in the demo.

Answer key — Exercise 1, the Black Friday storefront

Bottleneck: the database. App CPU is near 30%, but the database is at 98% CPU with all 100 of 100 connections used. The app servers are mostly waiting for a connection, and that is where the 6.2 s p99 comes from. Adding app servers makes it worse: each new server opens more connections against a pool that is already full, so more requests wait for the same overloaded resource.

Fixes, in order:

  1. Cache the product catalog (Redis, or a CDN for page parts). 95% of the load is reads of data that rarely changes, so this removes most of the database's work for very little code.
  2. Add a connection pooler, then read replicas for reads the cache does not cover. Send a user's reads to the primary shortly after they write (the read-your-own-writes rule from Part 3).
  3. Move the email call to a queue. It is not the bottleneck today, but it puts a 300 ms outside service inside every checkout.
  4. Store sessions in Redis and drop ip_hash.

The two hidden problems: sticky sessions with sessions in app memory (a server replaced mid-sale logs its users out, and heavy users can overload one server), and the inline email call (a slow provider slows or breaks checkout). Neither shows in the numbers yet.

Answer key — Exercise 2, the event pipeline that won't catch up

Two reasons the extra consumers did nothing. First, parallel work in a consumer group is limited by the number of partitions: three partitions means three active consumers, so consumers 4 to 6 are idle. Second, the load is not spread across those three. Merchant 7 is 68% of traffic and the key is merchant_id, so almost everything goes to P0. One consumer is at 100% CPU while the other two are at 3 to 4%. More consumers cannot split one partition.

Fixes and their costs:

  • Change the key (for example to order_id, or merchant_id plus a small random part for the big merchant). Spreads the load right away, but order is no longer guaranteed across one merchant's events, so check whether anything depends on it.
  • Add partitions (say 12). Raises the limit on parallel work, but changes where existing keys go, which can break order during the switch, and does nothing for a hot key by itself.
  • Make the consumer faster (batch the inserts). No risk to ordering, but it only helps by a constant amount.

Next to give out: the single Postgres writer. Once all consumers run, they all insert into one table. Batching, idempotent upserts, or partitioning the table come next. It is the Part 1 lock problem again, one layer down.

Answer key — Exercise 3, more replicas, same outage

Bottleneck: the primary. It is at 97% CPU taking every write (4,200/s) while the three replicas sit under 20%. Replicas only serve reads, and each also has to replay the same writes, so a third replica adds nothing for write capacity and a bit more copying work for the primary. Replicas scale reads, never writes.

The "old address" tickets are replication lag. Replication is asynchronous and p99 lag is 4 seconds. A customer saves an address (a write to the primary), and then the confirmation page reads from a replica that has not received it yet. Fix: for a short time after a user writes, read from the primary (or use a session-consistent read).

Scaling writes: partition (shard) the orders table. Shard key: customer_id, because the main queries are "this customer's orders", which then touch exactly one shard. Consistent hashing keeps resharding to a small fraction of keys. Each shard is its own primary with its own replicas, so the replica servers are reused. Keys to reject: a date or auto-increment id used as a range key (the newest shard takes every new write, the hotspot), and a hash of order_id (spreads writes evenly but scatters each customer's orders across all shards). Multi-master is not the answer here: two nodes accepting writes to the same order is exactly the conflict problem from Part 3.

What gets harder: queries and transactions that cross shards (reports, joins across customers), a very large customer making one shard hot, and changing the shard layout later. Analytics and cross-customer reports usually move to a separate data warehouse fed from the shards.
