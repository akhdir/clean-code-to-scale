Part 1 · 0:00–0:55

Scaling web and API requests

Request-serving is the part of a system that scales out most naturally — if three things are true: the instances hold no state of their own, you've decided on purpose where a user's session lives, and a thousand requests never end up queued behind a single row.

Three levers, one precondition

Vertical, horizontal, and functional scaling solve the same problem with different tradeoffs. Only one of them is free to reach for — and it has a precondition the other two don't.

Vertical — scale up

  • A bigger machine. No code changes, simplest lever to pull
  • Hard ceiling: there's always a biggest instance size
  • One box is one point of failure

Horizontal — scale out

  • More machines running the same code, behind a load balancer
  • Cheap and near-linear at first — but requires statelessness, and the payoff curves below
  • Redundancy comes free: lose one instance, the rest keep serving

Functional — split by responsibility

  • Decompose a monolith so each piece scales to its own load profile
  • Isolates failure — one overloaded piece doesn't take down the rest
  • Trades function calls for network calls — Day 7's whole subject

Stateless vs. stateful

The precondition is statelessness: an instance remembers nothing about a user between two requests. That doesn't mean the system has no state — it means the state lives somewhere other than the web tier.

Stateful instanceStateless instance
Where a user's data livesIn this process's memory — a cart dict, a session objectIn a shared store (Redis, the database) or inside the request itself
Which instance can answerOnly the one holding the dataAny of them
An instance diesEvery user on it loses their session and cartNothing is lost; the load balancer routes around it
Autoscale or deployUsers get logged out; instances can't be removed freelyInstances are disposable; scaling is invisible to users

Session handling: three ways to remember a user

Login state and shopping carts have to live somewhere. There are three common answers, and the choice is a real tradeoff, not a best practice.

ApproachHow it worksStrengthTradeoff
Sticky sessionsThe load balancer pins each user to one instance (a cookie, or a hash of their IP). Session data stays in that instance's memoryNo code change; works with an app that's already statefulThe instance is still the source of truth — see the issues below
Shared session storeInstances keep nothing; each request looks the session up in Redis (or similar) by a session ID in a cookieAny instance serves any request; instances are disposableOne extra network hop per request, and the store is now critical — it needs its own replication and failover
Client-held tokenThe session lives in the request: a signed token (e.g. JWT) the client sends every time, verified without a lookupNo server-side session storage at allHard to revoke before expiry; size limits; anything sensitive must be encrypted, not just signed
nginx.confsticky sessions in two lines
upstream checkout {
    ip_hash;                     # same client IP -> same instance, every time
    server app-a:8000;
    server app-b:8000;
    server app-c:8000;
}
Why sticky sessions are a bandage, not a fix
  1. Uneven load. A handful of heavy users pinned to the same instance can saturate it while the others idle — and the load balancer is no longer allowed to rebalance them.
  2. An instance dies, its sessions die with it. Every pinned user is logged out or loses their cart, in the middle of the sale.
  3. Deploys and autoscaling fight it. Removing an instance means draining it for as long as its sessions live, or logging those users out.
  4. IP hashing misleads. Thousands of people behind one corporate NAT all hash to the same instance.
  5. It hides the bug. A stateful app behind sticky routing looks fine in testing and in normal traffic — right up until an instance is replaced under load.

Demo: a flash sale finds the empty cart

The obvious fix — add eight more instances of the same size behind a load balancer. Nine instances at ~800 req/s each covers 6,000 req/s with room to spare. It doesn't work: customers start seeing empty carts mid-checkout.
checkout_service.py — statefulbreaks the moment a 2nd instance exists
# carts lives in this process's memory only
carts = {}

def add_to_cart(session_id, item):
    carts.setdefault(session_id, []).append(item)

def get_cart(session_id):
    return carts.get(session_id, [])
Why nine instances made it worse, not better
  1. Request 1 (add to cart) lands on instance A. carts in A's memory now has this customer's item.
  2. Request 2 (view cart) lands on instance C, chosen by the load balancer with no idea request 1 ever happened. C's carts is empty for this customer.
  3. The bug was always there — one instance just always answered both requests, so it never showed.
checkout_service.py — statelesscart lives in Redis, not in the process
def add_to_cart(session_id, item):
    redis.rpush(f"cart:{session_id}", item)

def get_cart(session_id):
    return redis.lrange(f"cart:{session_id}", 0, -1)
Talking points
  1. Same two functions, same call sites — only where the state lives changed. That's usually true: statelessness is a persistence decision, not a rewrite.
  2. Now any of the nine instances can answer either request, because none of them are the source of truth — Redis is.
  3. One more lever, cheap and easy to miss: the product-price lookup this whole flow depends on was hitting the database on every single cart operation. A cache in front of it (same Cache box in the diagram) cuts database load without adding a single instance.
  4. Sticky sessions would have hidden this bug: each customer keeps hitting the instance that holds their cart, so it works — until that instance is replaced mid-sale and every pinned customer's cart vanishes at once.

1,000 requests, one row

Stateless instances can multiply freely — until they all need to change the same thing. A flash sale on one product means one stock value, and every buyer has to decrement it.

buy.py — beforethe row lock is held across a slow call
def buy(product_id, user_id):
    with db.transaction():
        row = db.query_one(
            "SELECT stock, price FROM products WHERE id = %s FOR UPDATE",
            product_id,
        )                                          # row lock taken here...
        if row.stock < 1:
            raise SoldOut()

        payment_api.charge(user_id, row.price)     # ...and held through a ~200 ms network call

        db.execute("UPDATE products SET stock = stock - 1 WHERE id = %s", product_id)
        db.execute("INSERT INTO orders (user_id, product_id) VALUES (%s, %s)", user_id, product_id)

The lock exists for a good reason — two buyers must not both take the last unit. But a lock turns "many requests at once" into "one request at a time." For this row, the whole fleet runs serially, and the rate it can run at has nothing to do with how many instances you have:

Row lock held forMax updates per second, that one row1,000 requests drain in
200 ms (payment call inside the transaction)5200 s
20 ms5020 s
2 ms5002 s
0.2 ms (one atomic statement; illustrative)5,0000.2 s

Throughput on a hot row is 1 / lock-hold-time. Nine instances, ninety instances — the same five buyers per second get through. Worse, all the others are not idle; they are waiting, and waiting is not free:

0 s

The sale opens. 1,000 buy requests land across 9 instances. One gets the row lock; 999 wait — and each waiter is holding an application thread and a database connection while it does.

2 s

The connection pool fills (say it holds 100). Now requests that have nothing to do with the sale — browsing, login, the cart — can't get a connection either. The whole site slows down, not just the buy button.

5 s

Timeouts trigger retries. Clients and the load balancer give up and try again — but the abandoned transactions are still running server-side, queued on the same lock. Every retry adds a waiter instead of removing one.

10 s

Health checks start failing (they touch the database too). The load balancer pulls "unhealthy" instances out of rotation, so the survivors take more of the load and fail faster.

15 s

The failure leaves the building. Every service that calls checkout is now blocked on a call that won't return — the same cascade Day 7 dissects, started by one hot row.

buy.py — afteratomic update, slow work outside the lock, bounded wait
# at pool setup, once per connection:  SET lock_timeout = '300ms'  -- wait briefly, then fail fast

def buy(product_id, user_id):
    reserved = db.execute(
        "UPDATE products SET stock = stock - 1 WHERE id = %s AND stock > 0",
        product_id,
    )                                              # check + decrement in ONE statement
    if reserved == 0:
        raise SoldOut()

    try:
        payment_api.charge(user_id, price)         # slow call, no DB lock held
    except PaymentFailed:
        db.execute("UPDATE products SET stock = stock + 1 WHERE id = %s", product_id)
        raise                                      # give the unit back

    db.execute("INSERT INTO orders (user_id, product_id) VALUES (%s, %s)", user_id, product_id)

That fix is the first of several. Reach for them roughly in this order:

MoveWhat it doesWatch out for
1. Shrink the critical sectionHold the lock for one statement; slow calls (payments, emails) happen outside itA failure after the reserve needs a compensating step, as above
2. Atomic conditional updateSET stock = stock - 1 WHERE stock > 0 — no read-modify-write windowStill serial per row; it's just fast enough to stop mattering
3. Bound the waitlock_timeout, a small connection pool per endpoint, fail fast and shed loadDon't auto-retry blindly — a retry storm re-creates the pile-up
4. Optimistic concurrencyA version column; no lock while "thinking", retry only on conflictGreat when conflicts are rare. With 1,000 contenders almost everyone conflicts and retries — worse than the lock
5. Split the hot valueTen stock buckets, each buyer picks one at random — contention drops 10×Reads must sum the buckets; the last few units need care
6. Take it off the database's pathAn atomic counter in Redis (DECR), reconciled to the database asynchronously — or put the purchase on a queue (Part 2)Two systems that must eventually agree

Before the math: does 2× the machines give 2× the work?

Every lever above gets judged by one question: if I add resources, how much more work gets done? Horizontal scaling's pitch is the best possible answer — double the machines, double the throughput. The ratio has a name, speedup: how many times more work per second N machines do than one machine. Perfect scaling means speedup = N.

Your checkout fleet is close to that best case. Every request is independent — instance B never needs to know what instance A is doing — so doubling the instances really does roughly double requests per second. It holds right up until the instances all lean on something they share — like the hot row you just saw. That shared thing is the entire story of this section, and it breaks the straight line in two different ways:

1. Work that can't be split

  • Some step has to happen one-at-a-time, in order, on one machine — a lock, a final summary write, a single primary database
  • Engineers call that the serial part. Extra machines can't help with it, no matter how many you add

2. Instances having to talk

  • Instances that share state have to coordinate — invalidate each other's caches, agree on a lock, replicate a write
  • That chatter costs time, and it grows with every instance you add

Start with the first one, in real code. A nightly job recalculates every customer's loyalty tier, then writes the results to one summary table. On a single machine it takes 100 minutes:

loyalty_job.py — one machine100 minutes, start to finish
def recalculate_loyalty_tiers(customers):
    tiers = {}

    # part 1: per-customer work — every customer is independent of every other
    for customer in customers:
        tiers[customer.id] = compute_tier(customer.orders)   # ~95 min, all customers

    # part 2: the summary write — one table, one lock, one writer at a time
    with summary_table.lock():
        summary_table.write_all(tiers)                       # ~5 min
        summary_table.write_totals(tiers)                    # needs every tier first

Part 1 is the easy kind of work to share out: customer 7's tier never depends on customer 8's, so ten machines can each take a tenth of the customers. Part 2 can't be shared out: the totals need every tier first, and the table lets only one writer in at a time. Now split the job across N machines:

loyalty_job.py — N machinespart 1 shrinks, part 2 doesn't
def tier_chunk(chunk):                                       # runs on every machine at once
    return {c.id: compute_tier(c.orders) for c in chunk}

def recalculate_loyalty_tiers(customers, machines):
    chunks = split(customers, parts=len(machines))
    partials = run_on_each(machines, tier_chunk, chunks)     # ~95 / N min
    tiers = merge(partials)

    with summary_table.lock():                               # still one writer
        summary_table.write_all(tiers)                       # still ~5 min
        summary_table.write_totals(tiers)
Total time = 95 / N + 5 minutes. With 4 machines that's 23.75 + 5 = 28.75 minutes; with 20, 4.75 + 5 = 9.75; with 1,000, 0.095 + 5 = about 5.1. The 5 never moves — only the 95 shrinks. That 5 out of 100 is what "5% serial" means, and it's the number behind every row below. Here's what it costs in capacity you pay for:

Nothing is broken in that table — each added machine just buys a little less than the last one. The same thing happens to a fleet serving live requests, but it's harder to see there: you can't put a stopwatch on "the serial part" of live traffic. In checkout, it's the lock on the hot row: the part of the work only one request can be inside at a time. A batch job lets us time every piece, which is why we use it as the stand-in — and it sets up Part 2, where the job gets real.

The math behind the ceiling

The table above is Amdahl’s Law at work; here it is drawn out as a curve, next to a second, less forgiving one. "Add more instances" always has diminishing returns — and past a point, it can make things worse, not better.

Worked example, continued — the nightly loyalty-points job. The job from the code above takes 100 minutes on one machine, and 5 of those minutes are the serial summary write — so s = 5/100 = 0.05, the same 5% plotted above. Part 2 · 0:55–1:30

Scaling backend jobs with queues

The loyalty job above had a hole in it: run_on_each(machines, tier_chunk, chunks) just worked. In a real system something has to hand each chunk to a machine, notice when a machine dies, and make sure no chunk is processed twice or forgotten. That something is a queue — and it isn't only for batch jobs. It's the standard answer for any work that doesn't need to finish before the customer gets a response.

Why put a queue in the middle

checkout.py — beforethe customer waits for every step
def place_order(order):
    save_order(order)
    send_receipt_email(order)        # ~300 ms, third party
    update_loyalty_points(order)     # ~150 ms
    notify_warehouse(order)          # ~400 ms
    return "ok"                      # ~850 ms later — and a failure in any step fails the order
checkout.py — afterpublish one message, return
def place_order(order):
    save_order(order)
    queue.publish("order-placed", {"order_id": order.id})    # ~2 ms
    return "ok"

# on any number of worker machines, running separately
def loyalty_worker():
    for message in queue.consume("order-placed"):
        update_loyalty_points(message["order_id"])

Decouples timing

  • The request returns when the work is accepted, not when it's finished
  • A slow email provider no longer slows checkout

Absorbs spikes

  • A burst of orders becomes a backlog, drained at whatever rate workers can sustain
  • Workers run at a steady load instead of the traffic's peak

Fails and scales independently

  • A crashed worker doesn't fail the order; its message goes to another worker
  • Add workers without touching the web tier

Day 3's Observer pattern was this same idea inside one process: the publisher doesn't know who reacts. A queue is Observer across processes — with durability, and with the new problems that come with it.

A queue absorbs spikes, not sustained overload. If 6,000 messages arrive per second and workers finish 800, the backlog grows by 5,200 every second — over three million messages after ten minutes. The queue didn't remove the waiting; it only moved it somewhere safer. You still have to add consumers, shed load at the producer, or accept a delay that keeps growing.

Scaling the consumers: competing consumers

The first move is the obvious one: run more workers on the same queue. Each message goes to exactly one of them, so throughput grows with the worker count — the same stateless, any-instance-will-do property from Part 1, applied to jobs. It stops being enough for two reasons: a single queue is still a single machine with a single head, and the moment order matters (two updates to the same customer, in order), several workers pulling from one line can no longer be trusted to preserve it.

Scaling the queue itself: partitions

To scale the queue, split it. Instead of one line there are P independent lines (partitions), possibly on different machines. A producer chooses the partition for each message by hashing a key — the same hash-the-key idea Part 3 uses to split a database — so every message with the same key lands in the same partition, in order. Each partition is read by one consumer at a time. Throughput now scales with P, and ordering survives, but only within a partition.

How Kafka does it: a partitioned log

A log, not a queue

  • Messages are appended and retained (by time or size), not deleted when read
  • A consumer just remembers its offset — it can rewind and replay
  • Several consumer groups read the same topic independently (loyalty, analytics, search)

Order and parallelism

  • Key → hash → partition: same key, same partition, in order
  • Order is guaranteed only inside a partition, never across them
  • Partitions in a topic = max consumers working in parallel in a group

Staying up

  • Each partition is replicated; one replica leads, the rest follow
  • acks=all waits for the in-sync replicas before confirming a write
  • A group coordinator reassigns partitions when a consumer joins or dies (a rebalance)
loyalty_worker.pya Kafka consumer that survives being redelivered
# producer side: the key decides the partition
producer.produce(
    "order-events",
    key=str(order.customer_id),         # same customer -> same partition -> in order
    value=json.dumps(event),
)                                       # producer configured with acks=all

# consumer side
consumer = Consumer({
    "group.id": "loyalty-workers",
    "enable.auto.commit": False,        # we decide when a message counts as done
})
consumer.subscribe(["order-events"])

while True:
    msg = consumer.poll(1.0)
    if msg is None:
        continue
    event = json.loads(msg.value())

    if not already_processed(event["event_id"]):    # redelivery is normal; be idempotent
        update_loyalty_points(event)
        mark_processed(event["event_id"])

    consumer.commit(msg)                # commit AFTER the work: a crash before this replays, never loses

What goes wrong, and how it's handled

Every one of these comes from the same place: the queue sits between two processes that can each fail independently.

Talking points
  1. The batch job from Part 1 becomes: publish one message per chunk, let a consumer group drain them. The serial summary step is now the fan-in — it still can't be split, so the ceiling hasn't moved.
  2. Duplicates aren't a Kafka bug to be fixed; they're the price of not losing messages. The only real question is whether the consumer can tolerate seeing one twice.
  3. "More consumers" and "more partitions" are different knobs. Consumers beyond the partition count do nothing; partitions beyond what you can later reshuffle hurt.
  4. Kafka isn't the only answer — SQS or RabbitMQ delete a message once it's acknowledged and don't retain a replayable log. Pick the log when you need replay or several independent readers.
Part 3 · 1:30–2:15

Scaling the database

Web instances and workers are copies of code, so they multiply freely. The database holds the one thing that can't be copy-pasted: the data. There are three escalating moves — copy it, let every copy accept writes, or split it — and the CAP theorem describes what each one gives up when the network misbehaves.

Step 1: primary and replicas (master–slave)

One node, the primary, accepts every write and streams its changes to one or more replicas; reads can be spread across all of them. (Older docs call these master and slave.) It's the cheapest way to scale a read-heavy service — no schema change — and it adds failover: if the primary dies, a replica can be promoted. What it cannot do is scale writes: there is still exactly one writer.

Replication modeWrite is confirmed when…StrengthTradeoff
Asynchronousthe primary has itFast writes; a slow replica never blocks anyoneReplicas lag; a primary crash can lose the last few writes that hadn't been shipped
Synchronousthe replica has it tooNo acknowledged write is lost on failoverEvery write pays the replica's latency, and a down replica can stall writes
Semi-synchronousat least one replica has itA middle path used by many production setupsStill slower than async; still bounded by the slowest of the chosen replicas

Failover has its own hazard: if the old primary is only unreachable, not dead, and a replica is promoted anyway, you now have two nodes that each believe they are the writer — "split brain." Real systems need a fencing step so the old primary can't keep accepting writes. And the everyday cost of asynchronous replicas is the one the team hit three weeks after adding them:

orders.py — beforeevery read hits a random replica
def get_order_confirmation(order_id):
    return db.read_replica().get_order(order_id)
What actually happened
  1. Customer updates their shipping address at checkout — a write, sent straight to the primary.
  2. The confirmation page loads a split second later and reads the order back — routed to whichever replica the load balancer picks.
  3. Replication lag is normally a few tens of milliseconds. This time it was enough: the replica answered with the address as it stood before the write. The customer saw their old address and assumed the site had reverted it.
orders.py — aftera read that follows its own write goes to the primary
def get_order_confirmation(order_id, session):
    if session.wrote_recently(order_id):
        return db.primary().get_order(order_id)
    return db.read_replica().get_order(order_id)
Talking points
  1. This isn't a network partition — nothing was unreachable (that's the CAP case, at the end of this part). It's replication lag: a normal, constant, small delay that becomes visible exactly when a user reads back what they just wrote.
  2. The fix is narrow on purpose: only reads that follow their own recent write go to the primary. Sending every read to the primary would erase the whole reason for adding replicas.
  3. This is the cost side of the read-replica lever — real, but specific and fixable, not a reason to avoid replicas altogether.

Step 2: multi-master — every node takes writes

If one writer is the bottleneck, let several nodes accept writes — typically one per region, so a customer in Cairo writes to a nearby node and a customer in Dublin to another, each replicating to the other. Write latency drops, and a region going down no longer stops writes everywhere. The price arrives the moment two nodes change the same row before they have heard about each other's change:

T+0 ms

Cairo node: customer 8842 changes their shipping address to "12 Nile St." and the write is acknowledged locally.

T+80 ms

Dublin node: the same customer, from their phone, changes it to "4 Quay Rd." Dublin hasn't received Cairo's change yet, so it acknowledges this one too.

T+200 ms

Replication catches up. Each node now receives the other's write. Both have a valid history; the two histories disagree, and neither node did anything wrong.

Someone has to decide what the row says — and the options all cost something:

Conflict strategyHow it worksTradeoff
Last write winsKeep the version with the later timestampSimple, and silently discards one customer's write. Clocks on different machines disagree, so "later" can be wrong
MergeCombine both: version vectors detect the conflict; mergeable types (sets, counters) are combined automatically (CRDTs)Correct when a merge has meaning; most business fields (an address) don't have one

replication.py — last write winswhose clock is right?
def apply_remote_write(local_row, incoming):
    if incoming.updated_at > local_row.updated_at:     # compares two different machines' clocks
        local_row.update(incoming)                      # the losing write is gone, with no error anywhere
Some operations don't survive this at all. Remember stock = stock - 1 from Part 1? On two masters, both nodes read "1 left", both decrement and both confirm — the last unit is now sold twice, and no timestamp rule can fix it. Counters and inventory need a single owner for the contested value, or a data type designed to merge.

Step 3: partitioning (sharding) — split the data

Replicas copy all the data, and multi-master copies the conflicts. To scale writes and storage without conflicts, give each node only part of the data — and each row exactly one home. Splitting a database naively is its own trap.

Partitioning, in one paragraph. Partitioning means splitting a dataset into pieces; sharding is the version where the pieces live on separate database servers. (Splitting by columns or by feature is vertical partitioning; here we mean splitting rows.) Concretely, sharding is splitting one dataset across multiple database instances, each holding a subset of the rows — instead of one orders table on one machine, four smaller orders tables on four machines, each one a full, independent database in its own right. Every write and read has to be routed to the one shard that actually holds that row, which is a job the application (or a routing layer in front of it) now has to do that it never had to do with a single database. The hard part was never the splitting — it's deciding, consistently, which row goes to which shard. That's what the rest of this section is about.

Mod hashing: simple, until N changes

The obvious way to pick a shard: hash the key into a number, then take that number modulo the shard count. hash("order_8842") might come out to some large number; with 4 shards, that_number % 4 gives a value from 0 to 3 — the shard index. It's fast, needs no lookup table, and spreads keys evenly as long as the hash function is decent.

The catch is sitting right inside the formula: N — the shard count — is one of the inputs. Change N, and the formula's output changes for almost every key, not just the new one. Here's the same 8 keys, mod 4 versus mod 5:

Consistent hashing: same idea, one change

Forget shard counts for a second and just picture a clock. Instead of 12 numbers, this clock has thousands, but the idea is the same — and instead of hours, it holds shards. Hash each shard's name and that's where it sits on the clock face:

shard Asits at 2 o'clock
shard Bsits at 5 o'clock
shard Csits at 8 o'clock
shard Dsits at 11 o'clock

Now hash a key the exact same way — order_8842 lands on 3 o'clock. The rule for finding its shard is almost embarrassingly simple: walk clockwise until you hit one. From 3 o'clock, the next shard around is B at 5 o'clock. Done — order_8842 lives on B. No modulo, no shard count anywhere in that rule.

Here's the payoff. Add a 5th shard, E, at 9 o'clock — right between C (8 o'clock) and D (11 o'clock). order_8842 at 3 o'clock doesn't care: it still walks straight to B at 5. Nothing about A, B, C, or D moved, because their positions were never computed from each other. The only keys that notice are the ones sitting between 8 and 9 o'clock — they used to walk all the way to D at 11, and now they stop early, at E. Everyone else's walk is identical to before E existed.

That's the whole mechanism. The diagram below draws the same rule on a real ring, with real keys, so you can see exactly which one moves and why the rest don't.

Consistent hashing solves one specific problem — rebalancing. It's one of four common ways to decide which shard a row lives on in the first place. Same orders table, split by customer_id, four different answers for where customer 8842 lives:

StrategyWhere customer 8842 livesStrengthTradeoff

None of these is strictly better. The right one depends on whether your queries need ranges, how skewed the key distribution already is, and how much operational complexity the team can carry.

Putting it together: partitioning plus replicas

These moves compose rather than compete. A production database is typically partitioned so writes and storage spread across shards, and each shard is a primary with replicas so reads scale and failover works. What partitioning costs in return: queries and transactions that span shards get slower and harder, a skewed key can still make one shard hot, and changing the shard layout later is an operation, not a config tweak.

The CAP theorem: what each design gives up

Any distributed data store has three properties you'd like: Consistency (every read sees the latest write), Availability (every request to a working node gets an answer), and Partition tolerance (it keeps operating when messages between nodes are lost). Partitions are not optional — networks fail whether you plan for them or not — so the theorem's real content is narrower: when a partition happens, you must choose between consistency and availability. Refuse some requests, or answer with data that may be stale or divergent.

DesignWhen the network splits…Leans toward
Single primary; all reads from the primaryThe cut-off side can't reach the primary and refuses both reads and writesConsistency
Primary with async replicas serving readsReplicas keep answering, possibly stale; writes still need the primaryAvailability for reads, consistency for writes
Multi-masterBoth sides keep accepting writes, then diverge and must reconcile laterAvailability — and the conflicts above
Partitioned (each shard primary + replicas)The shards on the far side of the split are unreachable; the rest keep workingConsistency per key, with a bounded blast radius
Two clarifications. "Consistency" in CAP means every reader sees the latest write; it is not the same word as the C in ACID transactions. And CAP says nothing about the other 99.9% of the time, when there is no partition and the real trade is latency against consistency — the PACELC refinement, which Day 7 returns to when the nodes are services instead of database replicas.
Talking points
  1. Every step above buys something by spending something: replicas spend freshness, multi-master spends agreement, partitioning spends query simplicity. CAP is the same ledger, drawn for the moment the network breaks.
  2. "Which one should we use?" is the wrong first question. Ask what your service does if a user reads stale data, and what it does if it refuses a write — the business already has an opinion, and it picks the row of the table.
  3. Notice that no design here avoids the problem; each just relocates it. That is why the capacity plan in the next block starts by asking where your service's shared resource is.
