0:00–0:35 · Concept

Layers, and the one rule that matters

Everything else today follows from one sentence: source code dependencies may only point inward. An inner circle can't know an outer one exists.

Belongs in the core

  • Entities & business rules that would still make sense with no computer at all
  • Use case orchestration — the steps a business process actually takes
  • Value objects and domain types owned by nobody but the business

Belongs at the edge

  • Databases, ORMs, and anything that speaks SQL
  • Web frameworks, HTTP routing, request/response shapes
  • Third-party SDKs, queues, and UI frameworks

The diagram's dashed arrow, in actual code — the same violation the demo's PlaceOrder/OrderRepository split avoids.

place_order.py + order.py — beforethe entity imports a DB driver
# order.py — Entities ring
# smell: the innermost ring importing an outer-ring library
import psycopg2

class Order:
    def __init__(self, id, items):
        self.id = id
        self.items = items
        self.status = "pending"

    def save(self):
        conn = psycopg2.connect("dbname=orders")
        cur = conn.cursor()
        cur.execute(
            "INSERT INTO orders (id, status) VALUES (%s, %s)",
            (self.id, self.status),
        )
        conn.commit()

# place_order.py — Use Cases ring
class PlaceOrder:
    def run(self, id, items):
        order = Order(id, items)
        # smell: looks harmless from here — the violation is one call away
        order.save()
        return order
Why this is the violation
  1. PlaceOrder.run() looks clean — it never imports psycopg2 itself. The violation is hidden one level deeper, inside Order.save().
  2. That's what makes this crossing worth drawing: it isn't always obvious at the call site. order.save() reads like an ordinary method call, not a warning that the innermost ring just imported the outermost one.
  3. Once it's there, swapping Postgres for anything else means changing Order — the one class meant to be the most stable thing in the whole system.
place_order.py + order.py — fixedthe use case receives a repository
# order.py — Entities ring, zero imports beyond the standard library
class Order:
    def __init__(self, id, items):
        self.id = id
        self.items = items
        self.status = "pending"

# order_repository.py — the port, owned by the Use Cases ring
class OrderRepository:
    def save(self, order):
        raise NotImplementedError

# place_order.py — Use Cases ring
class PlaceOrder:
    def __init__(self, repository):
        self.repository = repository

    def run(self, id, items):
        order = Order(id, items)
        self.repository.save(order)
        return order

# postgres_order_repository.py — Interface Adapters ring, implements the port
import psycopg2

class PostgresOrderRepository(OrderRepository):
    def save(self, order):
        conn = psycopg2.connect("dbname=orders")
        cur = conn.cursor()
        cur.execute(
            "INSERT INTO orders (id, status) VALUES (%s, %s)",
            (order.id, order.status),
        )
        conn.commit()
What moved
  1. PlaceOrder now receives a repository instead of asking Order to save itself — the same dependency-inversion move as Day 3's InventoryAlert kata, one layer up.
  2. Order.__init__ has zero imports beyond the standard library — testable with zero setup, no database required.
  3. The SQL, the connection, and the vendor-specific driver all live in PostgresOrderRepository, in the Interface Adapters ring — exactly where the request-trace diagram below puts it, using the same three class names.
0:35–1:10 · Live demo

Tracing one request through the layers

Draw this live rather than presenting the finished diagram — add one box at a time as you narrate the request's path, and let the room guess where the "implements" arrow has to point before you draw it.

Talking points
  1. PlaceOrder and its OrderRepository port are the only two boxes actually inside the boundary — they know nothing about Postgres, HTTP, or any framework.
  2. OrderController is just as much an adapter as PostgresOrderRepository — one translates HTTP into a use case call, the other translates a use case call into SQL. Both sit outside the core and depend inward on it.
  3. OrderRepository is a port: an interface defined by the inside, describing what the use case needs, not how it's fulfilled — drawn dashed here, the usual convention for an interface.
  4. PostgresOrderRepository implements that port from the outside; its dependency arrow points back in, even though the request keeps flowing out.
  5. Delete PostgresOrderRepository, or swap OrderController for a CLI entry point instead of HTTP — PlaceOrder doesn't change one line either way. That symmetry is the whole point of the sandwich.
