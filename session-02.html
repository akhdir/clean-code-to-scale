Karnaugh maps: simplifying messy conditionals

A 15-minute tool for one specific ugly shape: a function with 3–4 boolean flags and an if/elif chain nobody's sure is exhaustive. A Karnaugh map (K-map) is a grid layout of a truth table that makes redundant branches visible instead of algebraic — the same kind of tangle Day 1's report(csv, summary, verbose) kata untangled by hand, but with a tool that scales past what you can eyeball.

The rule — a free-shipping check with three independent flags: is_member (P), total_over_50 (T), is_promo_day (D). Someone encoded the business rule as one explicit if per case they could think of.
shipping.py — before4 branches, unclear if that's all of them
def qualifies_for_free_shipping(is_member, total_over_50, is_promo_day):
    if is_member and total_over_50 and is_promo_day:
        return True
    if is_member and total_over_50 and not is_promo_day:
        return True
    if is_member and not total_over_50 and is_promo_day:
        return True
    if not is_member and total_over_50 and is_promo_day:
        return True
    return False

Three booleans means 8 possible calls. Laying every one out as a truth table is the first step — and the only way to be sure the four ifs above are actually every True case:

A K-map plots the same 8 rows on a grid where every neighboring cell differs by exactly one input — so a rectangle of adjacent 1s is a pattern algebra would take several steps to spot:

Read straight off the map: output = (P·T) + (P·D) + (T·D) — true whenever at least two of the three conditions hold. That's not just shorter, it's a rule a person can actually say out loud:

shipping.py — afterthe truth table, not the branches
def qualifies_for_free_shipping(is_member, total_over_50, is_promo_day):
    return sum([is_member, total_over_50, is_promo_day]) >= 2

One more pattern: when the branches don't all check the same flags

The example above was tidy — every if tested all three flags. Real conditionals grow one incident at a time, and each fix usually only touches the flags that incident involved. That's harder to eyeball, but the truth table doesn't care how the code was written — it still has 8 rows.

The rule — flag a transaction for manual review: is_new_account (N), failed_attempts_high (F), unusual_location (L). Three incidents, three fixes, three different flag combinations.
fraud_check.py — before3 branches, no two check the same flags
def should_flag_for_review(is_new_account, failed_attempts_high, unusual_location):
    if is_new_account and unusual_location:
        return True
    if failed_attempts_high:
        return True
    if is_new_account and failed_attempts_high and unusual_location:
        return True
    return False

Same move — every combination, not just the three someone happened to write down:

Read off the map: output = F + (N·L). The bigger the group, the fewer variables it takes to name it — a pair drops one variable, a quad drops two. And the third if in the original, is_new_account and failed_attempts_high and unusual_location, sits entirely inside the teal block: every cell it could ever match already returns True from the failed_attempts_high check above it. It's dead code, and the map is what makes that obvious instead of debatable.

fraud_check.py — afterone redundant branch, gone
def should_flag_for_review(is_new_account, failed_attempts_high, unusual_location):
    return failed_attempts_high or (is_new_account and unusual_location)
Why this belongs before today's smells — a long parameter list of booleans, an if/elif chain that "grew one case at a time," a speculative flag nobody remembers adding: all three often turn out to be an unmapped truth table. Before assuming a tangle needs an object or a strategy pattern, check whether it just needs 10 minutes on a grid. Where it stops helping: past 4–5 boolean inputs a K-map gets as unwieldy as the code it's replacing — that's the point where a decision table, a lookup dict, or the Strategy pattern from Day 3 takes over.

  • Four flags means 16 rows — is_member (M), under_threshold (U), first_time_request (F), item_verified (V). Before you fill the table in: how many of the four do you expect to actually matter?

0:20–0:50 · Concept

A shared taxonomy of smells

Read all three columns aloud. The goal isn't to memorize a list — it's to leave with shared names for things everyone already senses but nobody's agreed how to describe.

Code smells

  • Duplicate code — the same logic in two places will drift; extract it before it does
  • Long parameter list — 4+ arguments is a struct hiding in plain sight
  • Feature envy — a function mostly reading another object's fields belongs on that object
  • Speculative generality — a flag or parameter added "just in case," used by no one
  • Shotgun surgery — one business change forces edits across five unrelated files

Error-handling smells

  • Swallowed exceptions — except: pass turns a bug into silence
  • Error codes as strings or None — the caller has to guess what "failed" means
  • Catching Exception broadly — you meant to catch one failure, you caught all of them
  • Error handling mixed with business logic — the happy path is buried inside a try
  • Retrying blindly — no backoff, no limit reasoning, a denial-of-service on yourself

DRY & YAGNI, as tests

  • DRY test: could you name the one place this rule lives, right now? If not, it's duplicated.
  • YAGNI test: does any caller today use this parameter or branch? If not, delete it.
  • Both are heuristics, not laws — three similar lines beat a wrong abstraction
  • Premature abstraction usually costs more than temporary duplication does

Exceptions vs. result types

Where Day 1 left off — process_checkout collapses every possible payment failure into one ambiguous outcome. A declined card, a network timeout, and a misconfigured gateway all look identical to the caller.
checkout.py — Day 1's ending point1 outcome for N failures
def process_checkout(order, customer, payment_gateway):
    total = calculate_total(order, customer)
    if not payment_gateway.charge(total):
        return {"status": "failed"}
    mark_order_paid(order, total)
    return {"status": "ok", "total": total}

Live-code both fixes below. CardDeclined and GatewayTimeout are exceptions the payment library already raises; PaymentDeclined and PaymentGatewayUnavailable are ours.

Approach AExceptions
class PaymentDeclined(Exception):
    pass

class PaymentGatewayUnavailable(Exception):
    pass

def charge_payment(payment_gateway, amount):
    try:
        payment_gateway.charge(amount)
    except CardDeclined as e:
        raise PaymentDeclined(str(e)) from e
    except GatewayTimeout as e:
        raise PaymentGatewayUnavailable(str(e)) from e

def process_checkout(order, customer, payment_gateway):
    total = calculate_total(order, customer)
    charge_payment(payment_gateway, total)
    mark_order_paid(order, total)
    return {"status": "ok", "total": total}

# the caller is forced to decide — no silent path through
try:
    process_checkout(order, customer, gateway)
except PaymentDeclined:
    notify_customer(customer, "card declined")
except PaymentGatewayUnavailable:
    schedule_retry(order)
Tradeoffs
  1. A declined card can't be ignored — it's either caught or it crashes loudly.
  2. Two distinct exception types replace one ambiguous boolean.
  3. Cost: every caller up the stack now needs to know which exceptions can cross this boundary.
Approach BResult type
class ChargeResult:
    def __init__(self, ok, reason=None):
        self.ok = ok
        self.reason = reason

def charge_payment(payment_gateway, amount):
    try:
        payment_gateway.charge(amount)
        return ChargeResult(ok=True)
    except CardDeclined:
        return ChargeResult(ok=False, reason="declined")
    except GatewayTimeout:
        return ChargeResult(ok=False, reason="unavailable")

def process_checkout(order, customer, payment_gateway):
    total = calculate_total(order, customer)
    result = charge_payment(payment_gateway, total)
    if not result.ok:
        return {"status": "failed", "reason": result.reason}
    mark_order_paid(order, total)
    return {"status": "ok", "total": total}

# every outcome is visible in what's returned
outcome = process_checkout(order, customer, gateway)
Tradeoffs
  1. Every outcome is visible in the return value — nothing hides in a try a caller might forget.
  2. A declined card isn't a bug, it's an everyday outcome — this treats it as data, not an interrupt.
  3. Cost: callers can still forget to check .ok — nothing forces them to, the way a raised exception does.
The point isn't "pick A or B." The smell Day 1 left behind was returning an ambiguous dict with no defined contract. Both fixes above remove that. Which one your team standardizes on is an architecture decision worth making on purpose — not by accident, one PR at a time.
