0:00–0:30 · Concept

A shared taxonomy of smells

Read all three columns aloud. The goal isn't to memorize a list — it's to leave with shared names for things everyone already senses but nobody's agreed how to describe.

Code smells

  • Duplicate code — the same logic in two places will drift; extract it before it does
  • Long parameter list — 4+ arguments is a struct hiding in plain sight
  • Feature envy — a function mostly reading another object's fields belongs on that object
  • Speculative generality — a flag or parameter added "just in case," used by no one
  • Shotgun surgery — one business change forces edits across five unrelated files

Error-handling smells

  • Swallowed exceptions — except: pass turns a bug into silence
  • Error codes as strings or None — the caller has to guess what "failed" means
  • Catching Exception broadly — you meant to catch one failure, you caught all of them
  • Error handling mixed with business logic — the happy path is buried inside a try
  • Retrying blindly — no backoff, no limit reasoning, a denial-of-service on yourself

DRY & YAGNI, as tests

  • DRY test: could you name the one place this rule lives, right now? If not, it's duplicated.
  • YAGNI test: does any caller today use this parameter or branch? If not, delete it.
  • Both are heuristics, not laws — three similar lines beat a wrong abstraction
  • Premature abstraction usually costs more than temporary duplication does
0:30–1:05 · Live demo

Exceptions vs. result types

Where Day 1 left off — process_checkout collapses every possible payment failure into one ambiguous outcome. A declined card, a network timeout, and a misconfigured gateway all look identical to the caller.
checkout.py — Day 1's ending point1 outcome for N failures
def process_checkout(order, customer, payment_gateway):
    total = calculate_total(order, customer)
    if not payment_gateway.charge(total):
        return {"status": "failed"}
    mark_order_paid(order, total)
    return {"status": "ok", "total": total}

Live-code both fixes below. CardDeclined and GatewayTimeout are exceptions the payment library already raises; PaymentDeclined and PaymentGatewayUnavailable are ours.

Approach AExceptions
class PaymentDeclined(Exception):
    pass

class PaymentGatewayUnavailable(Exception):
    pass

def charge_payment(payment_gateway, amount):
    try:
        payment_gateway.charge(amount)
    except CardDeclined as e:
        raise PaymentDeclined(str(e)) from e
    except GatewayTimeout as e:
        raise PaymentGatewayUnavailable(str(e)) from e

def process_checkout(order, customer, payment_gateway):
    total = calculate_total(order, customer)
    charge_payment(payment_gateway, total)
    mark_order_paid(order, total)
    return {"status": "ok", "total": total}

# the caller is forced to decide — no silent path through
try:
    process_checkout(order, customer, gateway)
except PaymentDeclined:
    notify_customer(customer, "card declined")
except PaymentGatewayUnavailable:
    schedule_retry(order)
Tradeoffs
  1. A declined card can't be ignored — it's either caught or it crashes loudly.
  2. Two distinct exception types replace one ambiguous boolean.
  3. Cost: every caller up the stack now needs to know which exceptions can cross this boundary.
Approach BResult type
class ChargeResult:
    def __init__(self, ok, reason=None):
        self.ok = ok
        self.reason = reason

def charge_payment(payment_gateway, amount):
    try:
        payment_gateway.charge(amount)
        return ChargeResult(ok=True)
    except CardDeclined:
        return ChargeResult(ok=False, reason="declined")
    except GatewayTimeout:
        return ChargeResult(ok=False, reason="unavailable")

def process_checkout(order, customer, payment_gateway):
    total = calculate_total(order, customer)
    result = charge_payment(payment_gateway, total)
    if not result.ok:
        return {"status": "failed", "reason": result.reason}
    mark_order_paid(order, total)
    return {"status": "ok", "total": total}

# every outcome is visible in what's returned
outcome = process_checkout(order, customer, gateway)
Tradeoffs
  1. Every outcome is visible in the return value — nothing hides in a try a caller might forget.
  2. A declined card isn't a bug, it's an everyday outcome — this treats it as data, not an interrupt.
  3. Cost: callers can still forget to check .ok — nothing forces them to, the way a raised exception does.
The point isn't "pick A or B." The smell Day 1 left behind was returning an ambiguous dict with no defined contract. Both fixes above remove that. Which one your team standardizes on is an architecture decision worth making on purpose — not by accident, one PR at a time.

def apply_discount(price, pct, code=None, is_admin=False, force=False, legacy_mode=False):
    if legacy_mode:
        return price
    if is_admin or force:
        return price * (1 - pct)
    try:
        return price * (1 - pct)
    except:
        return price

def apply_bulk_discount(price, pct, code=None, is_admin=False, force=False, legacy_mode=False):
    if legacy_mode:
        return price
    if is_admin or force:
        return price * (1 - pct) * 0.95
    try:
        return price * (1 - pct) * 0.95
    except:
        return price

def restock_item(warehouse, item_id, qty):
    for attempt in range(10):
        try:
            warehouse.update_stock(item_id, qty)
            return True
        except Exception:
            continue
    return False

def get_shipping_label(order):
    address = order.customer.profile.address
    return f"{address.city}, {address.zip_code}"
