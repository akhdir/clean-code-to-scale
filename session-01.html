0:00–0:25 · Concept

Reference: the three habits

Move fast here — this is a shared vocabulary for the rest of the day, not a lecture. Read the three columns aloud, then spend remaining time on the rename pairs below.

Naming

  • Intention-revealing: d tells you nothing, elapsed_days does
  • No disinformation: don't call a dict a _list
  • Pronounceable and searchable — you'll say it out loud in review
  • Classes are nouns, functions are verbs
  • One word per concept: don't mix fetch/get/retrieve for the same idea

Functions

  • Do one thing, at one level of abstraction
  • Prefer 0–2 arguments; 3+ is a signal to introduce an object
  • A boolean flag argument means the function does two things — split it
  • No side effects hiding behind an innocent name
  • Don't let a global variable change what a function returns — inject the dependency as a parameter instead, so the same call always behaves the same way
  • Extract until you can't, then stop — don't over-fragment

Formatting

  • Newspaper rule: most important idea at the top, detail below
  • One blank line = one concept boundary
  • Keep declarations close to where they're used
  • Indentation and line length are a shared contract, not a preference
  • Use a formatter (Black, Prettier, gofmt) and stop debating it

0:25–1:05 · Live demo

One checkout function, refactored on screen

Live-code the transformation from before to after yourself rather than pasting the finished version — let the room call out smells as you go. db, email, sms are stand-ins for real services.

checkout.py — before5 responsibilities, 1 function
# TAX is a global magic number with no unit or context
TAX = 0.08

# smell: verb with no object — process *what*?
# smell: o, u, p, n force the reader to memorize a lookup table
def process(o, u, p, send=True, n=False):
    total = 0
    for i in o["items"]:
        total += i["price"] * i["qty"]
    # smell: 1000 and 0.9 are business rules with no name
    if u["loyalty"] > 1000:
        total = total * 0.9
    tax_amt = total * TAX
    total = total + tax_amt
    try:
        ok = p.charge(total)
    # smell: swallows every failure, not just payment ones
    except Exception as e:
        ok = False
    if not ok:
        return {"status": "failed"}
    o["status"] = "paid"
    o["total"] = total
    db.save(o)
    # smell: send/n are boolean flags forking hidden behavior
    if send:
        if n:
            sms.send(u["phone"], "Order paid: $%.2f" % total)
        else:
            email.send(u["email"], "Order paid: $%.2f" % total)
    return {"status": "ok", "total": total}
Talking points — before
  1. process(o, u, p, send, n) — a call site like process(order, user, pay, True, False) tells the reader nothing without opening the function.
  2. 0.9 and 1000 are a discount rate and a loyalty threshold — real business rules, invisible as numbers.
  3. One function calculates, charges, persists, and notifies over two different channels. Five reasons for this function to change.
  4. except Exception: ok = False silently turns any bug into "payment failed."
checkout.py — after7 functions, 1 job each
TAX_RATE = 0.08
LOYALTY_DISCOUNT_THRESHOLD = 1000
LOYALTY_DISCOUNT_RATE = 0.10

def calculate_subtotal(items):
    return sum(item["price"] * item["qty"] for item in items)

def apply_loyalty_discount(subtotal, loyalty_points):
    if loyalty_points > LOYALTY_DISCOUNT_THRESHOLD:
        return subtotal * (1 - LOYALTY_DISCOUNT_RATE)
    return subtotal

def calculate_total(order, customer):
    subtotal = calculate_subtotal(order["items"])
    discounted = apply_loyalty_discount(subtotal, customer["loyalty"])
    return discounted + (discounted * TAX_RATE)

def mark_order_paid(order, total):
    order["status"] = "paid"
    order["total"] = total
    db.save(order)

def notify_by_email(customer, total):
    email.send(customer["email"], "Order paid: $%.2f" % total)

def notify_by_sms(customer, total):
    sms.send(customer["phone"], "Order paid: $%.2f" % total)

# smell fixed: verb + object, and it only orchestrates
def process_checkout(order, customer, payment_gateway):
    total = calculate_total(order, customer)
    # real error handling for a failed charge is Day 2's territory —
    # for now we let it fail loudly instead of swallowing it
    if not payment_gateway.charge(total):
        return {"status": "failed"}
    mark_order_paid(order, total)
    return {"status": "ok", "total": total}

# the caller decides how to notify — no more hidden flags
result = process_checkout(order, customer, gateway)
notify_by_email(customer, result["total"])
Talking points — after
  1. process_checkout reads as verb + object, and now only orchestrates — it delegates everything else.
  2. calculate_total and calculate_subtotal are pure: no database, no network, easy to unit test in isolation.
  3. LOYALTY_DISCOUNT_THRESHOLD puts the business rule in one named place instead of buried in an if.
  4. The flags are gone. Notification is a separate call the caller makes on purpose.
  5. We did not fix error handling — flag that honestly. It's next session's topic, not swept under this one.

Kata B — Extract responsibilities
~20 minCore
TaskBreak this into single-purpose functions: validation, hashing, persistence, and notification should each be their own function. Remove skip_email the same way the demo removed send/n — by moving the decision to the caller.
signup.pystarter
def register_user(email, password, skip_email=False):
    if "@" not in email or "." not in email:
        return {"error": "invalid email"}
    if len(password) < 8:
        return {"error": "weak password"}
    has_digit = False
    for c in password:
        if c.isdigit():
            has_digit = True
    if not has_digit:
        return {"error": "weak password"}
    hashed = hashlib.sha256(password.encode()).hexdigest()
    user_id = str(uuid.uuid4())
    users_db[user_id] = {"email": email, "password": hashed}
    if not skip_email:
        email_service.send(email, "Welcome!")
    log.info("user registered: " + user_id)
    return {"id": user_id}
  • Which parts are validation, and which are side effects (writing to a db, sending email, logging)?
  • If this needed a unit test tomorrow, where would you draw the boundary to test password strength without touching the database?
  • If an AI agent were asked to change only the password rule, which version — this one or your refactor — gives it a smaller, safer diff to produce?
Done when
  • Email format and password-strength checks are separate, independently testable functions
  • register_user reads as a short list of steps, not a wall of logic
  • skip_email no longer exists as a parameter
Kata C — Flatten the flags
~10 minStretch
TaskThree boolean flags produce eight possible calls, and some are duplicated logic in disguise. Find the duplication, then propose — in words or code — a shape that doesn't require testing all eight paths.
report.pystarter
def report(data, csv=False, summary=False, verbose=False):
    if csv:
        if summary:
            return to_csv(aggregate(data))
        return to_csv(data)
    if summary:
        if verbose:
            return to_text(aggregate(data), detail=True)
        return to_text(aggregate(data))
    if verbose:
        return to_text(data, detail=True)
    return to_text(data)
  • Of the 8 possible flag combinations, how many are actually meaningful? What happens to the rest?
  • As a QE, how many test cases does this function need today — and how many after your redesign?

STANDARD_RATE_PER_KG_KM = 0.5
EXPRESS_RATE_PER_KG_KM = 1.2

def calculate_shipping_cost(weight_kg, distance_km, is_express):
    if is_express:
        return weight_kg * distance_km * EXPRESS_RATE_PER_KG_KM
    return weight_kg * distance_km * STANDARD_RATE_PER_KG_KM
Answer key — Kata B (one valid shape) 
MIN_PASSWORD_LENGTH = 8

def is_valid_email(email):
    return "@" in email and "." in email

def is_strong_password(password):
    return len(password) >= MIN_PASSWORD_LENGTH and any(c.isdigit() for c in password)

def hash_password(password):
    return hashlib.sha256(password.encode()).hexdigest()

def save_user(email, hashed_password):
    user_id = str(uuid.uuid4())
    users_db[user_id] = {"email": email, "password": hashed_password}
    return user_id

def send_welcome_email(email):
    email_service.send(email, "Welcome!")

def register_user(email, password):
    if not is_valid_email(email):
        return {"error": "invalid email"}
    if not is_strong_password(password):
        return {"error": "weak password"}
    user_id = save_user(email, hash_password(password))
    log.info("user registered: " + user_id)
    return {"id": user_id}

# caller decides whether to send the welcome email
result = register_user(email, password)
send_welcome_email(email)
