0:00–0:45 · Concept

Three levers, one precondition

Vertical, horizontal, and functional scaling solve the same problem with different tradeoffs. Only one of them is free to reach for — and it has a precondition the other two don't.

Vertical — scale up

  • A bigger machine. No code changes, simplest lever to pull
  • Hard ceiling: there's always a biggest instance size
  • One box is one point of failure

Horizontal — scale out

  • More machines running the same code, behind a load balancer
  • Cheap and near-linear at first — but requires statelessness, and the payoff curves below
  • Redundancy comes free: lose one instance, the rest keep serving

Functional — split by responsibility

  • Decompose a monolith so each piece scales to its own load profile
  • Isolates failure — one overloaded piece doesn't take down the rest
  • Trades function calls for network calls — Day 7's whole subject

The math behind the ceiling

"Add more instances" isn't free of diminishing returns — and past a point, it can make things worse, not better.

Worked example — the nightly loyalty-points job. One machine recalculates every customer's loyalty tier in 100 minutes. Profiling shows 5 of those minutes are unavoidably serial — acquiring a lock and writing the final summary table — so s = 5/100 = 0.05, the same 5% plotted above. Amdahl's formula, speedup(N) = 1 / (s + (1−s)/N), turns that into a schedule:
Machines (N)SpeedupJob time
11.0×100 min

10016.8×5.95 min
∞ (the ceiling)20×5 min — never less
No matter how many machines run this job, it can never finish faster than 5 minutes — the time the serial 5% takes on its own. That's what the asymptote in the chart actually means: a floor, not a suggestion. Going from 20 to 100 machines buys 3.65 fewer minutes; going from 1 to 20 bought 90.

Scaling data, not just compute

Stateless instances scale by copy-paste. A single database doesn't — it has to be split, and splitting it naively is its own trap.

Sharding, in one paragraph. Sharding is splitting one dataset across multiple database instances, each holding a subset of the rows — instead of one orders table on one machine, four smaller orders tables on four machines, each one a full, independent database in its own right. Every write and read has to be routed to the one shard that actually holds that row, which is a job the application (or a routing layer in front of it) now has to do that it never had to do with a single database. The hard part was never the splitting — it's deciding, consistently, which row goes to which shard. That's what the rest of this section is about.

Mod hashing: simple, until N changes

The obvious way to pick a shard: hash the key into a number, then take that number modulo the shard count. hash("order_8842") might come out to some large number; with 4 shards, that_number % 4 gives a value from 0 to 3 — the shard index. It's fast, needs no lookup table, and spreads keys evenly as long as the hash function is decent.

The catch is sitting right inside the formula: N — the shard count — is one of the inputs. Change N, and the formula's output changes for almost every key, not just the new one. Here's the same 8 keys, mod 4 versus mod 5:

Every key in this sample moved shard. At real scale that means the moment you add capacity, nearly the entire dataset has to be copied to new shards before the system is even usable again — the opposite of what "add a shard" was supposed to buy you.

Consistent hashing: same idea, one change

Forget shard counts for a second and just picture a clock. Instead of 12 numbers, this clock has thousands, but the idea is the same — and instead of hours, it holds shards. Hash each shard's name and that's where it sits on the clock face:

shard Asits at 2 o'clock
shard Bsits at 5 o'clock
shard Csits at 8 o'clock
shard Dsits at 11 o'clock

Now hash a key the exact same way — order_8842 lands on 3 o'clock. The rule for finding its shard is almost embarrassingly simple: walk clockwise until you hit one. From 3 o'clock, the next shard around is B at 5 o'clock. Done — order_8842 lives on B. No modulo, no shard count anywhere in that rule.

Here's the payoff. Add a 5th shard, E, at 9 o'clock — right between C (8 o'clock) and D (11 o'clock). order_8842 at 3 o'clock doesn't care: it still walks straight to B at 5. Nothing about A, B, C, or D moved, because their positions were never computed from each other. The only keys that notice are the ones sitting between 8 and 9 o'clock — they used to walk all the way to D at 11, and now they stop early, at E. Everyone else's walk is identical to before E existed.

That's the whole mechanism. The diagram below draws the same rule on a real ring, with real keys, so you can see exactly which one moves and why the rest don't.

Consistent hashing solves one specific problem — rebalancing. It's one of four common ways to decide which shard a row lives on in the first place. Same orders table, split by customer_id, four different answers for where customer 8842 lives:

StrategyWhere customer 8842 livesStrengthTradeoff
Range-basedIDs 8000–8999 → Shard CRange scans ("customers 8000–8999") stay on one shardNew signups get sequential IDs — the newest shard absorbs all new write traffic
Hash (mod N)hash(8842) % 4 → Shard BEven load, no hotspotAdding a 5th shard reshuffles roughly 80% of all keys overnight
Consistent hashingPlaced on the ring above, owned by the nearest shard clockwiseEven load, and adding a shard remaps only ~1/N of keysRange scans are gone entirely; needs "virtual nodes" per shard or load stays uneven
Directory-basedLooked up in a shard-map service → Shard DTotal flexibility — rebalance any single key on its ownThe directory is a new bottleneck and single point of failure unless it's scaled too

None of these is strictly better. The right one depends on whether your queries need ranges, how skewed the key distribution already is, and how much operational complexity the team can carry.

Read-heavy services often reach for read replicas before sharding — more copies of the whole database, reads spread across them, writes still going to one primary. It's cheaper than sharding and doesn't touch the schema. It also has a cost that shows up later, in today's demo.

0:45–1:15 · Live demo

A flash sale finds the ceiling

Walk through this as a narrative, live — the numbers first, then the code that explains them.

800 req/sComfortable baseline
6,000 req/sFlash sale peak
100%CPU, single instance
The obvious fix — add eight more instances of the same size behind a load balancer. Nine instances at ~800 req/s each covers 6,000 req/s with room to spare. It doesn't work: customers start seeing empty carts mid-checkout.
checkout_service.py — statefulbreaks the moment a 2nd instance exists
# carts lives in this process's memory only
carts = {}

def add_to_cart(session_id, item):
    carts.setdefault(session_id, []).append(item)

def get_cart(session_id):
    return carts.get(session_id, [])
Why nine instances made it worse, not better
  1. Request 1 (add to cart) lands on instance A. carts in A's memory now has this customer's item.
  2. Request 2 (view cart) lands on instance C, chosen by the load balancer with no idea request 1 ever happened. C's carts is empty for this customer.
  3. The bug was always there — one instance just always answered both requests, so it never showed.
checkout_service.py — statelesscart lives in Redis, not in the process
def add_to_cart(session_id, item):
    redis.rpush(f"cart:{session_id}", item)

def get_cart(session_id):
    return redis.lrange(f"cart:{session_id}", 0, -1)
Talking points
  1. Same two functions, same call sites — only where the state lives changed. That's usually true: statelessness is a persistence decision, not a rewrite.
  2. Now any of the nine instances can answer either request, because none of them are the source of truth — Redis is.
  3. One more lever, cheap and easy to miss: the product-price lookup this whole flow depends on was hitting the database on every single cart operation. A cache in front of it (same Cache box in the diagram) cuts database load without adding a single instance.

Epilogue: read replicas buy headroom, with a catch

Reads still outpace what the cache absorbs, so the team adds two read replicas — writes go to the primary, reads spread across three databases. Three weeks later, a support ticket: "your site changed my address back."

orders.py — beforeevery read hits a random replica
def get_order_confirmation(order_id):
    return db.read_replica().get_order(order_id)
What actually happened
  1. Customer updates their shipping address at checkout — a write, sent straight to the primary.
  2. The confirmation page loads a split second later and reads the order back — routed to whichever replica the load balancer picks.
  3. Replication lag is normally a few tens of milliseconds. This time it was enough: the replica answered with the address as it stood before the write. The customer saw their old address and assumed the site had reverted it.
orders.py — aftera read that follows its own write goes to the primary
def get_order_confirmation(order_id, session):
    if session.wrote_recently(order_id):
        return db.primary().get_order(order_id)
    return db.read_replica().get_order(order_id)
Talking points
  1. This isn't the CAP theorem's partition scenario from Day 7 — nothing was unreachable. It's replication lag: a normal, constant, small delay that becomes visible exactly when a user reads back what they just wrote.
  2. The fix is narrow on purpose: only reads that follow their own recent write go to the primary. Sending every read to the primary would erase the whole reason for adding replicas.
  3. This is the cost side of the read-replica lever — real, but specific and fixable, not a reason to avoid replicas altogether.

Why 70%, not 95%? Queueing delay scales roughly with ρ/(1−ρ), where ρ is utilization. At 70% that factor is 2.3×; at 90% it's 9×; at 95% it's 19×. The closer a service runs to fully utilized, the more a small traffic bump turns into a large latency spike — the safety margin above isn't caution for its own sake, it's what keeps the queue from blowing up.
  • What's your service's actual bottleneck — CPU, memory, or a downstream dependency? A capacity plan without a named bottleneck is a guess wearing a spreadsheet.
  • If your service isn't stateless today, what's the smallest piece of state you'd need to externalize first?
  • Where would a cache buy the most headroom cheaply, before reaching for another instance?
  • Is your data layer sharded, replicated, or a single instance? If a single instance is the actual bottleneck, more app-server instances won't touch it.
Done when
  • You have real or best-estimate numbers for every row above
  • Your instance count includes explicit redundancy, not just a bare minimum
  • You know whether your service is actually stateless — and if not, what blocks it

Prep

Facilitator notes

Before the session
  • Bring real traffic or capacity numbers for at least one team service if you can — "here are our actual numbers" lands harder than the worked example alone
  • The worked example's math is deliberately simple arithmetic (800 → 2,400 req/s, 750 req/s/instance, +1 redundancy) — resist making it more sophisticated than the room needs
  • Have the stateful-cart code ready to trace live, pointing at exactly which request lands on which instance and why it fails
  • Some pairs won't have real numbers for their own service — let them use rough estimates or reuse the worked example, and steer their discussion toward the methodology instead
  • The Amdahl/USL chart is the one place this session gets genuinely theoretical — spend time on the qualitative point (coordination overhead can make more instances actively worse), not on deriving the formulas. Nobody needs to leave able to compute κ and σ by hand
  • The consistent-hashing ring only needs to land one idea: adding a shard remaps a fraction of keys, not all of them. Skip the deeper "how do you pick a hash function" rabbit hole unless the room pulls you into it
Reference — the worked example, restated

Checkout handles 800 req/s comfortably today. A flash sale in six months is expected to push that to 2,400 req/s. Load testing shows one instance holds 750 req/s before CPU crosses 70%. 2400 / 750 = 3.2, rounded up to 4 instances for the load itself, plus 1 more so the system survives a single instance failing — 5 total. None of this matters until the cart's state moves out of process memory and into Redis, which is why that fix comes first in the demo, not last.
